# Test harness

How a task proves its work with no person watching. Every tool is judged by its exit code.

| To prove | Use | Run |
|---|---|---|
| Every scene renders, and a `<slug>/mockup` scene matches the mockup | `scenes.py` | `python3 tools/harness/scenes.py [--only chat/]` |
| What a drawn element shows and where | `tests/support/tree.rs` | `cargo test -p <crate>` |
| The wire client speaks the recorded protocol | `crates/core/tests/support/replay.rs` | `cargo test -p yd-core` |
| The real app beside a real server | `journey.py` | `python3 tools/harness/journey.py [name]` |

**Scenes.** Writes `target/scenes/<pane>/<state>.png` and `.tree.json` for every registered scene, in parallel. After a `<slug>/mockup` scene it runs `tools/parity/parity.py --tree <tree> --pane <slug>` and fails on a non-zero exit; after `shell/everything` it runs the same check against the whole first frame (`--frame 1`: bars, strip and all eight panes together). A render in which Rune reports a broken layout (`rune: scroll viewport … 0 pt tall`) fails too. Open the picture beside the mockup still before calling a pane done.

**The report.** `python3 tools/parity/report.py --write docs/parity.md --pairs <folder>` reads what the scenes rendered and rewrites the table of `docs/parity.md` (one row a frame: scores, exceptions, what a person sees differ from `tools/parity/seen.json`) and saves each scene beside its still. `--numbers` prints the totals alone.

**Trees.** In a test file: `mod support;` then `use support::tree::{..}`. `by_key`, `by_text`, `rect`, `row_text` (words inside a keyed element, left to right), `assert_row`, `assert_size(tree, key, (w, h), tolerance)`, `assert_golden(tree, "tests/golden/x.txt")`. A golden is rewritten only with `YD_BLESS=1`; on a difference the fresh copy lands under `target/tmp` and the error names both. In `yi-desktop`, `support::scene::elements("daemons/sample")` draws a registered scene in process (no GPU); `scene::runtime` keeps the runtime for pointer and key input. `yd-panes` has `tree`; `yd-ui` defines it.

**Replay.** `Replay::fixture("approval-allow")?` reads `fixtures/wire/approval-allow.jsonl` and splits it into connections (each after the first opens with `initialize`). `replay.serve(UnixListener::bind(path)?)` accepts one client per connection on a thread and returns `Vec<Played>`; `play(&lines, stream)` plays one on a `UnixStream::pair` end. The player writes the server's frames and checks each client frame: a request by method (its id is mapped, and the recorded reply goes back under the client's id), a reply to a server ask by id and exact result. A stray, silent (5 s), garbled or extra frame is a `Mismatch` naming the recording line.

**Journeys.** A journey is `tools/harness/journeys/<name>.json`: `scene`, `steps` (Rune's `--script` events: `move`, `tap`, `drag`, `scroll`, `menu`, `mark`), and `expect` (`keys`, `texts` that the final tree must hold). The runner starts `yi serve --model faux/faux-1` with `HOME` and the socket under `target/journey/<name>/home`, runs the app headless there with that `HOME`, writes `out/end.png` and `out/end.tree.json`, stops the server by its pid and fails if anything under that folder is still running. Logs: `serve.log`, `app.log`. `starts` proves the app starts beside the server and exits cleanly. `just journey` then runs the daily journeys, `tests/journeys/daily/fixtures/*.json` through `tests/journeys/daily/run.py`: the app is given `--realtime --socket <home>/yi.sock`, so it connects to the private server, and every prompt is typed into its own composer. A journey there is `seed` (threads made over the wire first), `worker` (the cassette worker whose turns ask to run a command), `serve` (server flags) and `runs`, one app launch each with `steps` and an `expect` of `keys`, `texts`, `contains`, `files` and `absent`. `just journey approve` runs one by name.

**Wider journeys.** `tests/journeys/all/fixtures/*.json` run through `tests/journeys/all/run.py` (built on the daily runner) and add to a run: `size`, `shims` (programs put first on the app's PATH, e.g. the scripted language server of `crates/sources/src/lsp/fake`), `server` (what the runner does to the server while the app runs: `stop` or `start`, each `after` a state it can see: `connected`, `stopped`), and project and home `files`. Expectations add `bodies` (a pane draws words below its tab bar) and `absent_keys`. Each process is started as the leader of its own group and the journey fails if one is left; times land in `target/journey/all-times.json`. What the real binary cannot do without touching this Mac (Containers, Daemons, the debugger, a pane in a second window, a restart) is `crates/app/tests/journeys.rs`.
