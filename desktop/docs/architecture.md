# Architecture

Yi Desktop is a native Mac app: a client of Yi's server (`yi serve`), written in Rust, drawn with Rune. One window is a dense grid of panes; any pane can become its own window; the whole window can become one conversation. Read this, then `docs/conventions.md`, then `docs/rune-notes.md`, before any source.

## Crates

| Crate (folder) | Owns | May depend on |
|---|---|---|
| `yd-core` (`crates/core`) | Everything with no pixels: the model and its one `step`, feeds and tables, the grid maths, addresses, commands, tokens, settings, findings, trace, the wire client and reducer. Tested without a window. | `yi-types`, `serde`, `serde_json`, `thiserror` |
| `yd-sources` (`crates/sources`) | Things outside the app, each a feed on a worker thread. The only crate that starts a process. | `yd-core`, `yi-browser`, `yi-types` (the browser's input types), `vt100`, `rustix`, `base64` |
| `yd-ui` (`crates/ui`) | The window state (`Win`, `Hub`), the pane contract, and the engines on Rune: theme, kit, chrome, grid view, list, code, terminal, screen, menu, overlay, states. | `rune`, `rune-kit`, `vt100`, `png`, `yd-core` |
| `yd-panes` (`crates/panes`) | One module per pane, and the pane table. Most panes are data over an engine. | `yd-ui`, `yd-core`, `rune`, `rune-kit`, `rune-luau` |
| `yd-mac` (`crates/mac`) | Menu-bar status items. The only place `unsafe` may appear. | `objc2` family |
| `yi-desktop` (`crates/app`) | The program: the root view, the scene table, the shell, windows, notifications, the menu bar. A library plus a three-line `main.rs`. | all of the above, `rune-notify` |

Nothing depends upward. `yd-panes` never names `yd-sources`: a pane and its source agree on a feed's name and on what is asked of it, both declared once in `yd-core` (`feed::{FILES, CHANGES, TERMINAL, OPEN_FILES, WEB, REPORT, CONTAINERS, DAEMONS, FETCH}` and the typed `SourceCmd`). No crate spells a shared feed or command id as its own string.

## Primitives

| Primitive | What it is | Where |
|---|---|---|
| Model and Msg | One `Model` on the UI thread, shared by every window. `step(&mut Model, Msg) -> Vec<Effect>` is the only thing that changes it, and it is pure: the same model and message give the same result. | `core/src/model.rs`, `msg.rs` |
| Feed | A typed stream from a source (the wire is not a feed; see "The wire as built"): `FeedEvent` is reset, upsert, remove or status; `FeedStatus` is loading, live, empty, offline or error. Events fold into a `Table` per `FeedId`. A list reads rows through the `Rows` trait, which `Table` implements and a filtered or grouped view may too. | `core/src/feed.rs`, `row.rs`, `inbox.rs` |
| Grid | `Layout` is tracks, a slot for every pane, and the panes that are out; `Windows::place` gives one rectangle per pane and always fills the grid. Five saved layouts are data, and so are the layouts a person keeps (`Windows.own`). `GridMsg` changes it and never leaves a hole. A window is a grid of one or more panes. See "The grid as built". | `core/src/grid/` |
| Pane | A `PaneDef` in a static table: kind, view, scenes, commands, settings, and optionally its own tabs (`tabs`, `on_tab`) and how its keyed elements are found as things (`finder`). The view is `fn(&PaneCx, &mut Cx<Win>) -> El` and draws the body only: the chrome draws the one tab bar. `PaneCx` is the hub, the pane, whether it is in focus, and `edits`: the text fields the window drawing it edits. | `ui/src/pane.rs`, `panes/src/registry.rs` |
| Row list | A list pane is a `ListDesc` (kind, columns, tree, row height, what an opened row shows) over a feed's table. One row is open at a time, in place. An opened row's `Detail` is facts, a text block and buttons; a button may carry its own target (`aims`), its own words (`titles`) and a key to show (`hints`). See "The list engine". | `core/src/list.rs`, `ui/src/list/` |
| Thing and Address | A `Thing` is what a keyed element stands for: a label, an `Address` and an excerpt. An address is `yi://<kind>/<stable id>[#part]`. | `core/src/address/`, `kind.rs` |
| Command | `Command` is an id, a title, a key, the kinds it applies to and a `Route` (model, wire or a source). A use of one is a `Run` with a `Target`. Buttons, menus, the command box and shortcuts are rows of command tables. | `core/src/command/` |
| Tokens | One owned set of design values with Yi Dark as the default. A theme file sets some by name; a name it lacks keeps its default, and each fallback is named. | `core/src/tokens.rs`, `ui/src/theme/` |
| Code surface | Lines as virtual rows with gutter, marks, squiggles, hints, token hits and a slot between lines. | `ui/src/code/` |
| Terminal surface | A screen parsed by `vt100` on the source's thread, drawn with `rune::grid`. | `ui/src/term/`, `sources/src/pty.rs` |
| Screen surface | Pictures in through `Pixels`, input out, things drawn over it. | `ui/src/screen/`, `sources/src/browser.rs` |
| Script pane | A Luau script drawing with host pieces through `rune-luau`, reloaded live. | `panes/src/script_pane/` |

## Data flow and threads

```
yi serve ── socket ── reader thread ──┐                       ┌── writer thread ── socket
docker, launchd, git, PTY, … ── source threads ──► inbox ──► step ──► Model ──► views
                                                (bounded)      │
user: press, key, menu ── handler ── dispatch ────────────────┘──► Effects ──► sink
```

- **One UI thread** owns every window, the `Hub` and the `Model`. Nothing blocks it and nothing draws while idle.
- **Worker threads** (the wire's reader and writer, one per running source) are plain `std::thread`. There is no async runtime.
- **In**: a worker holds a `Sender` (or a `FeedTx`, which can send only its own feed's events). `send` queues a `Msg` on a bounded channel of 4,096 and calls the wake the app gave it; a full channel makes the worker wait, which is the backpressure. The window's `poll` calls `yd_ui::win::drain`, which steps up to 1,024 messages a frame and asks for another wake if more wait.
- **Out**: `step` returns `Effect`s (`Wire`, `Source`, `Window`, `Notify`). `dispatch` and `drain` hand them to the hub's sink, a closure the app installs; it sends to the writer thread, to a source's command channel, or to the window layer. With no sink (scenes, tests) effects are dropped, unless `Hub::hold` was called: a run that will connect holds up to 4,096 until the ready hook sets the sink, since frame 0 lays panes out (a shell's first size) before it.
- **Windows**: each window's state is a `Win` holding `Rc<RefCell<Hub>>`. `dispatch(win, msg)` steps the model, delivers effects, then wakes every other window with an empty `AppHandle::update`. Views borrow the hub with `try_borrow`; handlers with `try_borrow_mut`; no borrow is held across a dispatch.
- **State that is not in the model**: a pane's own state lives in `Hub.panes` (a `Local`, keyed by pane and type), so it travels with the pane between windows. Rune state that belongs to one window (drag states, an open menu) lives in `Win.local`, and the text fields a window edits in `Win.edits`: a map from `(pane or none, field name)` to the field, because Rune's `on_edit` must be handed a field for certain (`yd_ui::win::field(pane, "draft")`; the command box's is `(None, "command-box")`). Anything else Rune keeps per window (scroll offset, focus, hover) does not travel.
- **Time** enters as `Msg::Tick(Millis)` and with every wire event, whose time moves `Model.now` forward (the running app sends no tick). No code reads a clock inside `step`.
- **The app's own files are written by one worker thread**, `yd_ui::disk::Disk` (in `hub.panes` under no pane; started by `start::files`): theme files and the triage file. A job runs after every job asked before it; with no worker (a test, a scene) it runs where it is asked. Quitting lets the worker finish, then writes what no poll handed over.

## Composition instead of shared edits

Three aggregates are frozen and built from parts their owners define in their own files:

| Aggregate | Its parts |
|---|---|
| `Model` | `wire` (WC), `tables`, `grid` (GR), `attached` (CX), `findings` (FM), `settings` (ST), `trace` (TR), `tokens`, `now` |
| `Msg` | `Wire(WireEvent)` (WC), `Feed`, `Command(Route, Run)` (CMD), `Source(FeedId, SourceCmd)` (a typed ask of one source), `Grid(GridMsg)` (GR: Show, Resize, Even, Swap, Leave, Rejoin, Split, Close, Open, Moved), `Attach(AttachMsg)` (CX), `Triage(TriageMsg)` (FM), `Settings(SettingsMsg)` (ST), `Theme(Box<Tokens>)` (the theme in use changed: these tokens replace the model's), `Tick` |
| `Effect` | `Wire(Request)` (WC), `Source(FeedId, SourceCmd)`, `Window(WindowOp::Open or Close)` (GR, applied by WN), `Notify(Notice)` (NB) |

A task adds a field to its own part or a variant to its own message type and fills its own `step`. It never edits `model.rs` or `msg.rs`.

## Frozen files

The keystone owns every `Cargo.toml`, `lib.rs` and `mod.rs`, the contract files of `yd-core` (`ids`, `kind`, `pane`, `row`, `feed`, `inbox`, `list`, `tokens`, `model`, `msg`), `yd-ui`'s `win.rs`, `pane.rs`, `slots.rs` and `scenes.rs`, the three registries, the app's `root.rs` and `scenes.rs`, and the five list panes that are pure data (`assets`, `containers`, `vms`, `daemons`, `lsp`).

Every other file under a directory belongs to the task the plan gives that directory to. If you need a module the tree lacks, put it under a file you own: `pane.rs` may declare `mod rows;` in `pane/rows.rs`. If you need a change to a frozen file, say so in your report and stop short of making it.

## How to add things

| To add | Do this, in files you own |
|---|---|
| A built-in pane | Fill `crates/panes/src/<pane>/pane.rs`: replace the placeholder view, keep `DEF`. The pane table already points at it. A pane that is not one of the 25 kinds is a script pane. |
| A list pane | Fill `desc.rs` with a `ListDesc`: columns name the cell fields, `detail` turns a row into facts, a text block and command ids. The view is one call: `yd_ui::list::view::list(pane, kind, &DESC, table)`. |
| A feed | Fill your source file's `run(out: FeedTx, cmds: Receiver<SourceCmd>)`: send `Reset`, `Upsert`, `Remove`, `Status`; return when `cmds` closes. The feed table already has its row. A feed is named after the pane slug it fills, and the pane declares the same `FeedId`. More than one of a source is `FEED.instance(n)`. |
| A command | Declare `pub const X: CommandId = CommandId("pane.verb");` and a `Command` row in your pane's `DEF.commands`: that row is all it takes for the command box, the shortcut map and the Mac menu bar (when it names a `menu`) to have it. The `Route` decides who carries it out: `Model` is handled in `command::run`, `Wire` becomes a server request, `Source(feed)` reaches that source as `SourceCmd::Run`. A view runs one with `yd_ui::menu::command_box::run(win, tx, Run::new(X).on(target))`, which tries the window first, or with `dispatch(win, Msg::Command(route, run))` when it knows the route. A command two crates name is declared once in `yd-core` (`command::table::OPEN_FILE` is `code.open`). |
| A command only a window can carry out | Declare it in `yd-core`'s table, add its id to `shell::view::WINDOWED` and an arm to `shell::view::carry` (the sidebar, the zoom, the bell, pick mode and New chat are there). |
| A button of an opened row that needs the hub or another pane | Declare it in the pane's `DEF.commands` (`Route::Model`), write `pub fn carry(win, tx, command, target) -> bool` in the pane and add it to the chain in `shell::view::carry` (Agents, Trace, Logs and Settings are there). It returns false for a command or a target it cannot serve, and the press then says "not available yet". |
| A pane no saved layout holds | A row of `grid_view::picker::PANES` (`pane.show-<slug>`, "Show Trace"): the command box lists it, the Panes panel gives it a switch, and `grid_view::view::show_pane(win, tx, kind)` does the same from a handler. |
| A pane's finder | Set `DEF.finder`: `Some(Finder::Rows(&DESC))` for a list pane whose rows are its slug's feed, or `Some(Finder::Keyed(thing_at))` with `fn(&Hub, PaneId, &str) -> Option<Thing>` reading the pane's own keys (the code viewer's lines, a file row, a diff line). Pick mode, the boxes and the right-click menu then find its things; nothing in the root changes. |
| Right-click items | Rows of `yd_core::command::by_kind` for the `Kind` of the thing: `items(kind)` lists them, and each is a `Command` row like any other. The menu opens for whatever the finder returns under the pointer, else for the pane. |
| An ask of a source with arguments | A `SourceCmd` variant, sent with `dispatch(win, Msg::Source(feed, ask))`: `Input(bytes)`, `Resize { cols, rows }`, `Close`, `Root(folder)`, `Read(path)`, `Revert { file, hunk }`, `Screen(ScreenInput)` (a pointer, a wheel, a named key or typed text on a screen, in the picture's pixels), `Seen(bool)`, `Labels(names)`, `Readable(folder)`. Never a `Run` whose text the source parses. |
| A pane's own tabs | Set `DEF.tabs` to a `fn(&PaneCx) -> Tabs` built from your state or the model on every view run (each `Tab` has an id, a title, a count and the meta the bar shows while it is in front; `adds` gives the bar a `+`), and `DEF.on_tab` to hear `TabAsk::Show`, `Close` and `New`. A pane with one tab and a meta sets `tabs` alone. Without `tabs` the bar shows the tabs kept in `hub.panes` (`chrome::tabs::Tabs`), else one named after the kind. |
| The thread a pane shows | `pane.thread()`: the thread its window shows. Never the first listed thread, never a pick of the pane's own. |
| Opening a file | `yd_ui::grid_view::view::open_file(win, tx, address)` from a handler: it runs `code.open` and focuses the window's code viewer, opening one when the layout has none. |
| A scene | Add a `Scene { name, stage, setup }` to your `DEF.scenes` or your file's `SCENES`. `just scenes` renders it; a test draws it. Scene `I` runs in slot `I`; there are 256 slots. |
| A setting | Add a `Setting` row to your pane's `DEF.settings` (every text is a `Cow`, so it is a constant; choices are a `const` slice of their own). Read it with `model.settings.value("pane.key")`. |
| A setting that shows state kept elsewhere | A row as above, then two arms in `settings::pane::bind`: `state` says what the row should read, `apply` makes the state follow a change to the row. The theme, density, glass, chat side and layout rows are there. |
| A token | A colour is a named value in `theme::scale` (`Ink`, in `INK_GROUPS`, so the theme editor shows it; `docs/conventions.md` "Theme values"), read with `.of(tokens)`; a size is a `Num`. A view never spells a colour (`just colours`). A theme file may set any name; names the table lacks are kept in `Tokens.extra`. The shared tokens in `tokens.rs` are the record's own values and do not grow. |
| Pane state | A `Default` struct in your pane's module, read with `pane.state::<T>()` and changed in a handler with `hub.panes.get_mut::<T>(Some(pane))`. |

## The wire as built

`yd-core` holds the whole connection; it draws nothing. `core/src/wire/` has the client threads, `event`, `frame` (decode), `request` (encode) and `replay` (resume bookkeeping); `core/src/reduce/` folds frames into `Model.wire`.

- **A request is an id and a line.** `Request { id: Option<RequestId>, line: String }`: `line` is one JSON-RPC object with no newline; `id` is none when no answer comes (an answer to a server ask, a refusal). `RequestId` is `Number(u64)` (this app's own, in the order sent) or `Text`. Build one with `Request::call(n, method, params)`, `answer(id, result)` or `refuse(id, method)`; method names and param builders are in `wire/request.rs`.
- **`WireEvent`** is what the client's threads hand the UI, carried in `Msg::Wire`: `Line(String)` (an undecoded line, how a recording or scene feeds the model), `Frame { at, frame }`, `Up { at, server, latency }` (`latency` is how long the server took to answer `initialize`; a recording times nothing unless its row carries `took`), `Down { at, why: Down }`, `Unsent { at, id }` (a request the client could not write), `Poll { at }` (time to ask for the thread list), `Bad { at, why }`. `Frame` is `Update`, `Ask`, `Reply`, `Request` (a method this app lacks) or `Other(raw)`.
- **`Model.wire` is `Wire`**: `link` (`Starting`, `Up { server, since, latency }`, `Down { why, since }`), `threads` (by `ThreadId`), `asks`, `settings`, `failures` (last 32), `dropped`. Read it through `listed()` (pins first, then newest activity), `status(&id)`, `attention()` (the bell, dock badge and status items read this; no `Effect::Notify` comes from the wire), `waiting()`. A `Thread` holds `transcript` (`messages`, `turns()`, `tools`), `work` (todos, plan, goal, claims), `agents`, `usage`, `options`, `prefill` (words to put back in the composer), `notes`, `extras`, `sync`; `option("model" | "thought_level" | "mode")`, `cost()`, `unseen()`, `asker(call)`. Sequence checks, resume decisions, request ids and the table of pending requests are reducer state, so a recording tests them with no socket.
- **Wire command ids** (`core/src/reduce/step/commands.rs`, `Route::Wire`; `COMMANDS` is the menu subset for the command registry): `thread.new` (target a `place`; text is the first prompt), `thread.open`, `thread.close`, `thread.prompt`, `thread.cancel` (prompts typed during the turn then wait, `Wire::holds`, until `thread.send-queued`: the queue's Send, or Return in an empty composer), `thread.steer`, `thread.slash`, `thread.set-option` (text `option=value`), `thread.pin` (toggles), `thread.seen`, `thread.fork` (target a message `yi://message/<thread>/<entry>`; text `at` keeps the message), `thread.rewind` (text `files` restores files too), `approval.allow`, `approval.always`, `approval.deny`, `approval.answer` (text is the id of one of the options the ask offers; any other id changes nothing), `approval.cancel-all`, `settings.read`, `settings.write`.
- **An ask's options are typed.** `Ask::offers()` gives each `Offer { id: OptionId, name, kind: OptionKind }`; `OptionKind` is `AllowOnce`, `AllowAlways`, `RejectOnce`, `RejectAlways` or `Other(String)`. A view matches it exhaustively and draws every offer; no crate but `yd-core` names `yi-types`' option type.
- **A window is the view of the thread it shows.** `yd_ui::shown` keeps each window's pick (`hub.panes`, under no pane): `thread(hub, window)` is the picked thread, else the first root the list shows; `PaneCx::thread()` reads it for a pane; `show(win, id)` picks from a handler; `forget(hub, window)` drops a closing window's pick and returns the thread it had open; `fresh`, `start`, `sent` and `leave` are New chat's. `sync(win)`, which the window's `poll` calls every frame, runs `thread.close` for the thread the window showed and `thread.open` for the one it shows, and sends the `fs`, `git` and `lsp` sources `SourceCmd::Root` with the folder the thread works in (`shown::works_in`: the worktree `_yi/workdir` named, else the checkout the git feed lists on the thread's branch `yi/<id>` once that checkout holds work (its row's `changed`: it differs from the base), kept once seen, else its `cwd`). Yi sends `_yi/workdir` only to a client attached when the session attaches or moves, so a second client learns the checkout from git. So a thread that shows because the list arrived is opened like one that was pressed, and no pane opens or closes a thread itself. While that folder is not the thread's `cwd`, Files, Changes and Code draw one line at their foot (`files::pane::copy::under`, so nothing above it moves when it comes: "Agent's copy · yi/<short id> · from <project>/<base>"), whose press (`shown::flip_project`) points the three sources at the project folder instead, and back. The reducer counts views to decide when to resume (once, however many views show a thread), when to mark seen, and when to answer a closed thread's asks `cancelled` (only while the link is up).
- **A listed session's parent** is read from `_meta.yi.parentSessionId`, else `parentSessionId`, into `Thread::forked_from`, so a child made by another client nests under its parent. Yi's `session/list` does not send either yet.
- **Time** is injected: the client takes a `Clock` returning `Millis` in Unix epoch milliseconds, because the server's `lastEventMs`, `pinnedMs` and entry times are compared with it.
- **The thread list is asked folder by folder.** Yi answers `session/list` without a cwd with its daemon's live sessions only, and with a cwd with what that folder stored. Each poll asks once for each known project (`settings::store::PROJECTS`, the app's own setting, newest first, at most `MAX_PROJECTS` = 8) and once without a cwd, so at most nine lists; a folder's answer drops only threads of that folder, the plain one only threads of no known folder, and `listed` is set once the round's last list is answered.
- **Caps**: frame 32 MiB (`MAX_FRAME`, Yi's own console reads the same); out queue 256 requests (`OUT_QUEUE`); 100,000 messages a transcript; 10,000 threads; 64 asks; 1,024 child agents. A resume always asks for the whole branch and rebuilds the transcript.
- **Client**: `Client::spawn(Config { socket, poll, start }, inbox Sender, clock)` returns at once; `send(request)` never blocks and returns `Unsent::Full` or `Stopped`; `close(grace)` queues the stop behind what was already queued, so every request sent before it is written first, and returns `StillRunning` if the thread is not done within `grace` (a handshake can take up to 10 s). Dropping a client stops it at once. `yd-core` cannot start a process, so `start` is an injected `Starter` closure; it is not called while `<socket>.stopped` exists.
- The recordings in `fixtures/wire/` replay through the reducer alone or over a real socket (`crates/core/tests/support/replay.rs`).

## The grid as built

- **`Layout`** holds `cols` and `rows` (`Track::Px` or `Fr`), `areas` (a slot for every pane, including panes that are out) and `away` (a `Hole` per pane that is out, with the neighbours it remembers). `Windows { side, panes, windows, own }`; `Window { id, layout, saved, own, frame }`; `saved` is the saved layout's slug and `own` the kept layout's number, each until the user rearranges the window.
- **Layouts a person keeps** (`grid::saved::Own { id, name, shape }`) are kept in the grid's own file. A `Shape` is a layout by pane kind (tracks, and the kind each slot shows); `Shape::of` takes a window's layout as drawn, closed up round the panes that are out, and `Shape::picture(room, side, width)` is `place` at the window's size scaled to `width`, what the Panes panel draws. `GridMsg::Keep { window, name }` keeps the window's arrangement under the lowest number free from 6 (`OwnId`; 6 to 9 carry ⌥⌘6 to ⌥⌘9, at most 8 are kept, a name is 1 to 40 characters) and marks the window as showing it; `Wear` shows one, `Rename` names it again, `Forget` drops it and only unmarks a window that showed it. A file's kept layout that does not tile or is out of range reads as gone.
- **Draw with `Windows::place(window, size) -> Vec<(PaneId, Rect)>`**, already mirrored for chat on the left and closed up round panes that are out. Never iterate `layout.areas` for what is drawn. `line_at(window, size, Point)` is the drag hit test (3 point reach, columns before rows); `origin_of(pane).is_some()` means the pane is pulled out.
- **`GridMsg::Open { window, kind }`** shows a pane of a kind the window does not draw (one resting here, in its own slot; else a hidden one, else a new one, in half of the largest pane as the window draws them, cut across its longer side); asked again it changes nothing. The pane is the person's from then on and never rests. `show_pane` sends it and puts the pane in focus.
- **A layout is places, not panes** (`docs/layout.md`, stage 1). A pane a layout seated (`Pane.seated`, set by `Show` and `Wear` for every slot) is out of the grid while its kind has nothing to show: a `Hole` with `resting`, drawn in no window, closed up round like a pulled-out pane, and not pulled out (`origin_of` is none). `GridMsg::Have { window, kinds }` tells the grid the kinds with something to show; `step::settle` then rests each seated pane whose kind is missing and gives each resting one whose kind is there its own slot back, and `Show` and `Wear` settle too. Chat never rests, a pane pulled out of another window never rests, a pane the grid cannot close up round stays in, and before a window's first `Have` nothing moves. `Open`, and a drop of the pane, make it the person's (`seated` off). `Shape::of` counts a resting pane as present, so a kept layout keeps its place. A file from before this reads with nothing seated and nothing resting.
- **Panes belong to a session** (`docs/layout.md`, stage 2). A pane the person has carries `Pane.scope`: `Window` (every session of its window) or `Sessions(list)` (the threads they opened it in, the oldest forgotten past `MAX_SESSIONS`, 64). `GridMsg::Have` now carries the `thread` the window shows (none for New chat); `settle` rests the person's pane where that thread is not in its scope and gives it its slot back where it is, as it does a seated pane by its kind. The window keeps one layout, so the tracks, and every line, stay through a switch. A pane `Open` or `Split` makes is the session's shown (`Scope::new`), or the window's for a kind about this Mac or the app (`PaneKind::wide`: Assets, Containers, Daemons, Language servers, Plugins, Settings, Themes, VMs) and where no session is shown; `Open` in a second session opens the same pane, in its slot, in that session too. `Close` of a pane open in other sessions closes it in this one only (`step::shut_here`: it rests and keeps its slot); in its last session it is closed for good. `GridMsg::Across { pane, on }` (commands `pane.keep-across`, `pane.keep-here`, in the Window menu and ⌘K) moves a pane to the window's scope or back to the session shown. The window's own chat, the one a layout seated, always shows; a chat split from it is its session's. A pulled-out pane never rests. A file from before this reads every pane as the window's. A new thread no longer resets the window to the chat alone (`shown::made`): its session simply has no panes yet.
- **A slot holds a stack of tabs** (`docs/layout.md`, stage 3, first part). `Layout.stacks` lists the panes that share a slot, each list in tab order; one of them holds the slot in `areas` and is drawn, the rest are behind it (in no slot, drawn nowhere) or pulled out. A pane alone in its slot is in no list. `Layout::front(pane)` is the pane holding the slot `pane` shares, `Layout::holds` whether a pane is the window's at all, `Windows::home_of` its window, and `Windows::tabs(window, pane)` the panes of its stack that show here, which is what the bar draws. `leave::front` gives the slot to another tab by renaming it in `areas`, in a resting hole and in the neighbours other holes remember; a pulled-out pane keeps its own hole. Which tab is in front is no change of layout: `step::edit` names a slot by its stack's first tab, so a saved layout stays marked.
- **Opening goes to a place** (`PaneKind::place`: chat, work, side, shelf). `GridMsg::Open` brings a pane the window has in front (drawn, behind, or resting); else the new pane joins the first slot whose first tab is of the same place (`step::host`; never a pulled-out pane's slot nor a guest's) and comes in front; else it is cut half of the largest pane as before, and a side pane then lands as a column on the far side from the chat (`DOCKED`, 300 wide), a shelf pane as a row along the bottom (150 tall), where the minimums allow. `GridMsg::Front(pane)` is a press on a tab. `Close` of one tab among others gives the slot to the next (`leave::next_tab`: the one after, else the one before, one that is here before one pulled out); a carried pane takes its whole stack (`leave::vacate`); a tab pulled out keeps its place in the stack and docks back in front.
- **Settling** (`step::settle`, `settle_in` for one slot): the pane in front stays while it shows, else the first tab that shows takes the slot, and a slot none shows in rests. `Windows.fronts` remembers the tab in front of each stack as a window turns from a session, and puts it back in front when it turns back; it is not kept in the file.
- **A carried pane goes alone** (`swap::land`). A pane that is one tab among others leaves them the slot, with the tab after it, else the one just before, in front (`leave::next_tab`, which a closed tab uses too). Dropped on an edge it has a slot of its own; an edge of its own slot is a zone for it (`Spot::Beside` naming the pane itself) and cuts it from its tabs; dropped on another pane's middle it joins that pane's tabs in front, where a pane alone in its slot swaps as before. The slot it left settles for the session shown (`step::settle_in`), so a tab of another session does not take it. A pane out of another window takes no tab (`Windows::visiting`): its tabs are kept where it came from. `step::edit` counts the stacks in a layout's shape, so a tab moved to another slot unmarks a kept layout while a tab brought in front does not.
- **The bar** (`grid_view::view::slot_tabs`): the drawn pane's own tabs, with one tab in its place for each other pane of the stack (`chrome::tabs::Tab::stacked`, keyed `<drawn pane's key>.tab-pane-<n>.pane-tab`, always with a close cross). A press on one sends `Front` and moves the keyboard there; its cross closes that pane; pulled out of the strip it becomes a window. The tab keys (⌘⇧[ and ⌘⇧]) walk every tab of the stack, drawn or not. A bar draws as many of the other panes' tabs as it has room for at their least (`chrome::tabs::fits`, from the slot's width), the ones nearest the pane drawn first, and counts the rest in a `+N` chip (`<key>.pane-tab-more`) that opens the Panes panel, where each can be brought in front.
- **A pane about one thing** (`Pane.thing`, an `Address`, kept in the grid file as its text). `GridMsg::About { window, kind, thing }` shows the pane of that kind about that thing: the one the window has comes in front, a hidden one comes back, else a new pane joins the stack of its place. A pane about another thing is another pane; `Open` by kind alone means the pane about nothing. `PaneKind::place_about` puts a chat about a thing, a child agent's, in work beside the session's chat. A layout seats no pane that is about a thing, and a thing whose pane is out in a window of its own is not opened a second time. The first user is a child agent's chat, which retired the table `chat::pane::child::Children` and the `children` key of the window layer's file.
- **Not yet** (rest of stage 3, #2306): the one show action with who asked and how strongly (a quiet dot, the idle rule), built with its first caller, the rules of stage 4. A terminal per session as its own pane is not built: one pane already holds each session's shells (`Shown.parked`), so the person would see no change.
- **Which kinds have** (`yd_panes::has`): `has::tell`, called by each window's poll, sends `Have` when the kinds or the session shown changed. Files, Changes, Code, Web app, Remote desktop, Report and Terminal are tested (rows, a page, an open file, a written report, a command the agent ran or a shell that has printed; a feed's failure counts as something to show); every other kind always has. `root::init`, the window scenes and tests start from, asks for each of Everything's panes by `Open`, so none rests in a scene with nothing in it.
- **`GridMsg`** (in `Msg::Grid`): `Show { window, saved }` (slugs `everything`, `review`, `screens`, `code`, `just-chat`; also makes a window the grid lacks), `Keep`, `Wear`, `Rename`, `Forget` (above), `Resize { window, line, to, size }` (`to` is the pointer position along the axis, as drawn; absolute), `Even`, `Swap { window, a, b }`, `Drop { window, pane, at: Spot, size }`, `Leave(pane)`, `Rejoin(pane)`, `Split(pane)`, `Close(pane)`, `Moved { window, frame }`. `Leave` and `Show` return `Effect::Window(WindowOp::Open)` for a window they make, `Rejoin` returns `Close`; opening a window that exists is nothing to do.
- **Docking** (`grid::swap`): a carried pane lands at a `Spot`, its edges as drawn: `Onto(pane)` swaps; `Beside(pane, edge)` closes the carried pane up where it was (as `Close` does, no hole) and gives it the half of that pane's slot on that edge (`leave::split`: cut at a line the slot crosses, else its one track halved); `Side(edge)` closes it up and adds a full-height column or full-width row on that edge of the grid, `Px` 300 wide or 150 tall (`DOCKED`). `land` refuses a drop that would draw any pane of the window under the minimum (`GridError::Cramped`), so a refused drop changes nothing. `Windows::zone_at(window, size, pane, point)` is the hit test while a pane is carried: within 12 points of the grid's edge (`SIDE`) the window's edge, else over another pane its edge band (a quarter of its width or height from that edge, `BAND`; the band it is deepest in) or its middle; nothing over the carried pane's own slot. A `Zone` has the `spot`, its `band` and `lands`, where the pane would be drawn (none when refused), found by dropping on a copy. `Windows::toward(window, pane, edge)` is what the Move Pane keys aim at: `Beside` the pane drawn just past that edge, else `Side(edge)`, sized by `Windows::room` (the window's frame, else 1200 by 750).
- **The drag in the view** (`grid_view::drag`): a press on a bar or on a tab that cannot be reordered (its pane's only tab, or a tab the pane keeps itself) arms the pane (`Gesture::Armed`); it is carried only once the pointer has gone 4 points (`THRESHOLD`), so a click only shows the tab. While carried, `Held.at` is the pointer in the grid's points and the view draws `drag::preview`: the zone's `lands` filled with the accent (`grid.drop-zone`), or the band saying "Not enough room for a pane here" (`grid.drop-refused`). Release sends `Drop`; Escape cancels the drag in Rune and nothing changes. `pane.move-left`, `-right`, `-up`, `-down` (⌃⇧⌘ and the arrow; ⌃⌥⌘ arrows belong to window managers such as Magnet) move the focused pane the same way.
- **Limits**: pane minimum 160 by 120, window minimum 720 by 480 (`MIN_PANE`, `MIN_WINDOW`), 32 tracks an axis, 64 panes. Reading a saved grid checks it and refuses a file that does not tile, names a pane twice or an unknown kind.

## The window, the shell and the panes, joined

- **The window** (`app/src/root.rs`, as `spikes/glass` proved): `root::app()` is titled with `Titlebar::new(25)` (the top bar's height: full-size content, the traffic lights over the top bar, which is the drag region) and see-through (`WindowOptions { transparent: true }`). The root carries the window's one material, `SystemMaterial::Glass`, while the `glass` token is on (`root::material`); off, and in every headless picture, the root's own opaque fill (`window`) shows. The shell draws the tint as a child, over the wash: the mockup's muted desktop (a base lit from the top left, four hues, darker edges, a faint glow), the `wash.*` colours of `theme::scale`, painted at the `wash` strength (1 in Yi Dark; a theme's 0 lets the real desktop show through the glass).
- **Zoom** is Rune's page zoom (`Cx::zoom`), set by `root::zoomed` on every view run of every window, with the title band grown to match (`Cx::titlebar_height`). Its value is the setting `view.zoom` (`root::ZOOM`), kept in the settings file; ⌘= (and ⌘+), ⌘- and ⌘0 (`view.zoom-in`, `view.zoom-out`, `view.actual-size`, carried by the window) step it through `root::ZOOMS` or set 1. Only the native app declares the row, defaulting to 1.25 (the owner's pick, halfway between 1 and the 1.5 that made a 2056 by 1204 window read as the mockup's 1200 by 750); without it a scene or a test draws at 1.
- **The grid in the shell**: the slot keyed `shell.grid` holds `grid_view::view::grid`. `root::init` shows the saved layout `everything` in the main window, since the grid draws nothing for a window it does not hold; the native app with no places kept opens blank instead (`root::blank`: `saved::BLANK`, slug `chat`, the chat pane alone in the grid, beside the sidebar), and a thread New chat makes opens the same way (`shown::made`), unless the window shows Just chat. Panes appear when opened. Chat is on the left by default (`ChatSide::Left`); the grid's file names the side `chat`, so the old default an older build wrote as `side` is dropped once and a choice made since is kept. The grid is kept when a layout or its panes change, and once a resize has rested half a second (`windows::hub::hold`), so a killed app comes back as it was. The sidebar is open or hidden, never folded (`Shell.hidden`, kept with the thread shown); it is open by default and beside New chat too, its tree below New chat's title row so the lights sit over it. Its right edge drags its width between 160 (`sidebar::MIN_W`) and a third of the window, 196 by default (`sidebar::TREE_W`), which a double-click on the edge gives back; the width (`Shell.width`) is kept beside the thread shown and survives hiding. New chat (⌘N) and New project (Open Folder…, ⌘O) head it, their keys in their tooltips, and a folder New chat was pointed at is listed as a project before it has a thread. Every shell control runs its command with `shell::view::run(win, tx, command, target)`, which is `command_box::run`. A Terminal shell starts in the folder it kept, else the thread's project folder, else home (`start::starting_folder`): a kept folder that is empty or not a directory (a restored thread not yet listed, a released lane) is never started in, and the pane says which folder it took in one muted line.
- **The top bar's right end** is the bell and one Panes button (`grid_view::picker::BUTTON`, `layout.pick`, ⌥⌘0, View menu "Panes and Layouts"; its tooltip names the key). It opens the Panes panel (`grid_view::picker::layer`, drawn in the window's menu layer by `command_box::layer`, hung under the button, 300 wide, opaque `fill.popover`, modal: Esc or a press outside closes it, and so does choosing a layout; while a name is asked the first Esc or outside press only cancels the name, `picker::close`). The panel holds: a picture of each saved layout and each kept one (`Shape::picture` at the grid's own size, chat tinted, the one shown ringed, the tooltip its name and key), then `+`, which asks a name in a field in the panel (Return keeps it; past ⌥⌘9 the field says the layout gets no key); a right-click on a kept layout offers Rename and Delete, the saved five offer neither; the chat side as Left | Right; then every pane kind the grid shows (Settings and Themes open in a window and are left out) in two columns, each with a switch: on is `show_pane`, off closes every pane of that kind here as its bar's cross does; chat is always on. The panel is one focus group (`role` grid): it opens with the keyboard on the layout shown, arrows move through every item, Space and Return press. Kept layouts are run by `layout.own-6` to `layout.own-13` (`picker::OWN`); `picker::title` names each "Layout: <name>" for the command box, the key sheet and the Mac menus, which leave out a number nobody keeps. The panel's state is the window's `Grip` (`picking`, `naming`).
- **One tab bar a pane**: `chrome::tabs::bar` is the only bar. It shows `DEF.tabs` when the pane keeps its own (the terminal's shells and agent tab, the code viewer's open files, the meta of chat, files and changes), and a press, `cmd+w`, the tab keys, the `+` and each tab's close cross (drawn when the pane has `on_tab`) reach the pane through `DEF.on_tab`. A pane's own tab cannot be reordered or torn out. `Stage::Pane(kind)` draws `grid_view::view::alone`: the pane under the same bar, filling the window.
- **A message's usage** is typed: `Message::spent()` gives an answer's `Spent { cost, output }` (dollars, tokens written).
- **Opening a file**: `code.open` (`Route::Model`, target a `file` or `lines` address) is carried out in `command::run`: the file's row in the `code` table (`OPEN_FILES`: id `file:<path>`, cells `path`, `tab` (its tab's id for good), `opened` (the highest shows), `new`) becomes the newest, and the effect `Source(FILES, Read(path))` asks the `fs` source for its text, which lands in the `files` table as the row `file:<path>`. Files, a changed file's name in Changes and a file a chat step names all call `open_file`. **A look** is `code.open` with the text `preview` (`run::PREVIEW`; `grid_view::view::preview_file`): a file not open yet opens with the cell `preview` set and takes the tab of the last look, so any number of files looked at leave one tab; a look at a file already open brings it in front and changes no tab. Opened any other way the cell is cleared. The Files pane looks on a press and opens on a double press; the code viewer draws the preview tab's title in italics (`Tab.preview`), keeps it on a press while it shows, and only brings it in front on a press while another file shows.
- **The git feed's `repo` row** carries `branch`, `commit`, `ahead`, `behind`, `project` (the folder's name), `base` (where `origin/HEAD` points, else `main` or `master`), and `added` and `removed` summed over every change. On a Yi branch (`yi/…`) the changes are measured from the branch's merge base with `base`, committed or not, and the Changes bar names the checkout. A row `worktree:<branch>` (`path`, `changed`) names each checkout of the repository on a Yi branch. In a Yi checkout the row `merge` says what `changes.merge` would bring into the project's own folder (`branch`, `base`, `home`, `commits`, `files`) or why not (`refused`: that folder has uncommitted changes or is not on the base, or the branch has nothing new; `uncommitted` is `1` when the checkout's own work is not committed yet, and the pane then offers "Ask it to commit", which prompts the thread to commit), and what the last merge `said` (`done` counts them). The Changes bar's "Merge into <base>" asks first; the source checks again and runs a plain `git merge --no-ff` there, a conflict left as git left it. Yi frees the checkout and deletes the merged branch when its session ends.

## The list engine

All in `yd_ui::list`, drawn on `virtual_rows`:

| Entry | Use |
|---|---|
| `view::list(pane, kind, &DESC, table)` | A whole list pane: header bar, column titles, rows, footer. |
| `view::part(pane, kind, name, &DESC, table)` | A list inside a pane that draws more; keys are `<pane key>.<name>.*` and it has its own open row. |
| `view::stream(...)` | `part` that follows its newest row unless the reader scrolled up or a row is open. |
| `row::key`, `row::id_of`, `row::thing(&DESC, row)` | From a row to its key, from a picked key to its row id, from a row to its `Thing`. |
| `state::Lists` (in `hub.panes`) | `list_mut("").set_open(Some(id))` opens a row; `ListState::open`, `cursor`, `at_tail`. |

A list takes the fast path (a versioned key list, rows built on demand) only when its table is `tables.get(FeedId::new(kind.slug()))`; any other table is copied each view run, which only suits small lists. A group's summary is read from a cell named `group.summary` on the group's first row.

A list narrower than its columns drops them from the right, never the name column, which keeps at least 120 points (`view::dropped`, from the width `ListState` heard on layout).

A detail's facts share one label column, 56 points wide unless the detail sets `label: LabelWidth(..)` (the Language servers list does, for "Agent may ask it").

**A detail button** (`list/detail.rs`) is found by id in the whole table (`command_box::table`: `yd-core`'s rows, the grid's, every pane's), so a pane may list a wire or attach command by its own id. Its words are the detail's `titles` entry, else the table's title; its key hint is the detail's `hints` entry, else the command's key. A press runs `command_box::run` with the detail's `aims` entry as target, else the row's own address (`yi://<kind>/<row id>`), else the pane. When nothing carries the command out (`NotBuilt`, `Unknown`) the list says "<title> is not available yet" beside the buttons (`ListState::said`), until another press or another row; no pane writes that note into its rows.

## The running window, as joined

- **One start-up, many windows** (`app/src/root.rs`, `windows/hub.rs`, `start.rs`). `main` calls `root::run(native)` with `!rune::is_headless()`; nothing else asks Rune whether the run is headless. `run` makes the one hub and hands `rune::run_windows` the specs of `windows::hub::specs`: the main window (`root::main`), a window for each pane that was out, and the hidden spares of a headless run. Every window's Rune hooks are set in `Registry::window` and each hook kind is set once: close (`hub::closed`), focus (`hub::front`, which tells `notify::focus`), visibility, and quit (`root::quit`: the window layer keeps its places, then `start::quit` answers every waiting ask `cancelled` and stops the client and the sources). The main window alone has the ready hook: `start::start(win, app, native)`, then for the native app `notify::ready` (dock badge, status items). `notify::install` puts the Mac menus on the main window's `App` before it runs.
- **`start::files(hub, Files)`** reads the user's own files, for the native app only (`root::run`; `Files::app()` is the config folder `yi-desktop/`, `Files::under(folder)` is a test's): the themes folder (`theme::files::open`), then the settings file (`settings::pane::file::restore`, after the folder's themes are the theme row's choices) and the theme it names under `appearance.theme` (`bind::theme`), then the folder plugin panes are looked for in, `panes/` (`script_pane::pane::open`), then the triage file (`triage::open`). It starts the disk worker. A triage file that did not read and could not be moved aside is never saved over (`Loaded::may_save`).
- **`start::start`** makes the inbox, the wire client (clock in Unix ms, a starter that spawns `yi serve` detached) and the effect sink: `Wire` to the client (a refused request comes back as `Unsent`), `Source` to its source (started on its first ask: a shell by `pty::serve` with its tab's screen, a page by `browser::serve` with its pane's, any other by the registry's row), `Window` to `windows::hub::reconcile`, `Notify` to `notify::post`. A run that is not the native app connects only when `--socket <path>` names a server, so a scene or a test never reaches `~/.yi`.
- **`root::poll`**, every window's: `windows::hub::poll` (make the real windows the grid's), `start::settle`, `drain`, `shown::sync`, `notify::poll` (the bell, notices, badge, status items, the threads held open for their asks), the code hover tick, `lsp::marks::follow` (opens the file a go-to-definition named once its `def:` row has come), `theme::files::tick` (the main window alone: it hears how theme writes went, looks at the themes folder once a second, hands edits to the worker and asks for the next look's wake, so an idle window notices a changed file and draws nothing otherwise), `script_pane::pane::tick` (the main window alone, as the themes: plugins load and reload, timers run, fetches are asked, other windows are woken when a picture changed), `settings::pane::bind::follow` (the rows that show state say what the state is; the theme in use is kept in the settings file), `seen::poll` (see "What the wave 8 joins do"), `start::keep` (the triage goes to the worker when its revision has moved). The native app puts one status item in the menu bar (`menubar::start`): its title is what needs you (`● 2`), else what is working (`◐ 1`), and its menu lists both. Closing the last window quits the app and the item with it (the owner's first look; it was `keep_running`). One app runs a home folder (`windows::single`): the first launch locks `running.lock` in its config folder; a second one with the same HOME writes `show.ask` and exits, and the first's main-window poll brings every window forward when it finds the ask. Instances with their own HOME run side by side.
- **Closing the main window** while a pane's window is still up only puts it away: its thread stays open and its asks wait; closing the last window quits, which cancels them. Closing a pane's window sends the pane home and closes the view of its thread (`shown::forget` drops the window's pick and what it had open).
- **A window's root** is `root::dressed(win, hub, cx, key, body)`: the body under `overlay::boxes::over` (boxes round what is attached, the pick layer), `rune_kit::root` with `command_box::layer` (the command box and the right-click menu), paste, the right-click press, the fill and the one material. The main window's body is the stage's; a pane's window draws `grid_view::view::grid`, which gives a lone pane's bar the title-bar height (23) and room for the traffic lights when the window is not the grid's first.
- **Keys**: `AppSpec.on_key` of every window is `root::on_key`: Esc closes the bell's panel, else leaves New chat; then `command_box::keys` closes a menu or runs the command the shortcut map (`Keys`, built from the whole table) gives the key.

The opened box takes the keyboard (`Tx::focus_when_shown`).

## Invariants

- `step` is pure. It does no I/O, reads no clock and starts nothing.
- No hole, ever: `place` covers the grid exactly for any layout, size and chat side. Fixed tracks shrink together before a shared track would fall under the pane minimum.
- A feed that goes offline or fails keeps its rows. A table never holds more than 200,000 rows; the oldest go and are counted in `Table::dropped`.
- An address is built from a record's id, never from display text. `yi://tools` and `yi://skills` belong to Yi and are refused.
- At most twelve things are attached to one prompt.
- Every element a user can point at has a key that starts with its pane's key.
- No crate but `yd-sources` starts a process. No crate but `yd-mac` has `unsafe`.
- A not-built body says so: a placeholder view names its task, a source reports an error status, a step returns no effects. Nothing panics. (`GridError::NotBuilt` is gone: the grid is built.)
- A grid change happens whole or not at all: one that cannot be made changes nothing and returns no effects.
- A frame the server sends, a pane in a window and a request in flight are each bounded; see the caps under the wire and the grid.

## Trust boundaries

| Boundary | Assume | Control, and who builds it |
|---|---|---|
| The socket to `yi serve` | Frames are bytes from another program: any length, any shape, newer than this app. | A bounded read per frame (32 MiB), a line over it or not JSON is skipped and counted in `Wire.dropped`, typed decode with raw maps for unknown shapes, sequence checks in the reducer. WC. |
| A source's child process (`docker`, `launchctl`, `git`, a language server, a debug adapter, a shell) | Its output is hostile text. | Started by absolute path with an argument list, never a shell string; bounded lines; a timeout on every wait; killed with its group. Each source's owner. |
| Web content in the browser pane and scripts in a script pane | They run code the user did not write. | Chrome is a separate process; a frame is refused by its header, before anything is allocated, past 8,192 a side or 8,192 by 4,320 pixels in all (`screen::surface::MAX_PIXELS`); Luau runs in `rune-luau`'s sandbox with its watchdog and heap cap; a plugin's web answers are 64 rows in all. WB, PL. |
| What a page says of its own elements in design mode | The page runs the script that answers, so every name, colour, number and word is the page's to choose. | Typed decode, a wrong shape refuses the whole answer; a name is cut to 128 characters, a source location and a page to 512, words to 512, each between characters; a length is held within a million pixels of zero and a colour is `#rrggbb` or a dash; a typed value reaches the script only as JSON data, after `Property::checked`; 64 questions wait at most and 64 elements are tracked (`sources/src/cdp.rs`). DM. |
| Theme, settings, triage and fixture files | The user can edit them. | Parsed into typed values; a value that does not fit is refused by name and the old one kept. Nothing indexes or slices by a number from a file. A theme file is at most 256 KiB, a triage file 4 MiB; one that does not read is kept aside or left alone, never written over. |
| An address pasted or sent by an agent | Attacker-chosen text. | At most 2,048 bytes; `%XX` escapes must decode to UTF-8; direction marks are escaped when printed. |
| Text from the server shown to the user | It may carry control and direction characters. | Set as text, never parsed as markup beyond the Markdown renderer. CH. |

## Fallbacks applied from the spikes

- The window keeps the Mac's own corner radius: a titled window with traffic lights cannot take the record's 10 px.
- The opaque window is one token, `glass`: off, the root's own fill (`window`) is drawn, which is also what every headless picture shows.
- Layouts glide on the mockup's own curve through `Tx::motion_curve`; no spring.
- The code surface is rows, not `rune::grid`. Copy of a file past 10,000 lines gives a prefix (Rune's cap).
- The terminal keeps its own scrollback; `vt100` 0.15 cannot scroll past one screen.
- Shells start through the installed `yi __pty`.
- The wire client keeps its own queue of approval requests and tolerates unknown event kinds.
- Hover in a window that is not key does not follow the pointer: the patch to the fork's window layer is described in the wave 5 notes and not made.
