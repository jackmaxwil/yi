With `YI_CLAUDE_HOOKS=1`, a Yi agent obeys the `PreToolUse`, `PostToolUse` and `PostToolUseFailure` command hooks of the Claude Code user who launched it, the same ones a Claude subagent runs. They fire around every tool call in root sessions and children, around a cell's MCP call through `yi mcp`, and, for Bash hooks, before the shell checks a goal, plan or schedule runs, under Claude's tool names and argument shapes. An edit reaches an Edit hook once per file, with the changed text as `old_string` and `new_string`.

Hooks never weaken Yi's gates. A hook's allow only answers the question the permission mode would have asked, and is journaled as the hook's answer; a configured ask rule, a hold, a credential read, a deny rule and a catastrophic path still stand, the call stays in the sandbox, and an in-process write is held to the sandbox's write roots. A hook's ask goes to the person and is refused headless. Several hooks combine deny over ask over allow, and a `defer` is ignored, as Claude ignores one outside a single-call `-p` run.

Project settings that carry hooks run only after `yi trust` grants their exact content; until then they are skipped with one notice. Because hooks run on the host, the project's `.claude` directory is closed to the sandbox's writes, and every in-process write there is a question no hook can answer. The configuration is read once when the root session starts and shared with its children. It comes from the project Claude Code names in `CLAUDE_PROJECT_DIR` when Claude Code launched Yi in a worktree, and a plugin can be listed by its install root. A hook inherits Yi's environment as Claude's inherits Claude's. A hook that ignores its stdin, sleeps past its timeout, floods its stderr or is interrupted no longer hangs or fails open, and the handlers for every file of an edit run at once. Text past Claude's 10,000-character cap is kept whole in a session file and named with a preview. Handler types and fields Yi does not support are skipped with a notice that says they fail open.
