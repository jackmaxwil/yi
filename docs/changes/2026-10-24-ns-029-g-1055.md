A spawn's `check` now meets the gate an armed command does. The check runs `sh -c` on the host when the parent calls `rlm.result`, outside the sandbox, and until now nothing judged it: a user's gate rule that would have stopped the same command in a bash call, an `exec://` heartbeat source or an armed todo let it through. The host gets the gate the wiring already builds for heartbeat sources (`tools::heartbeat_gate`, renamed `host_gate` since it now serves both), so the check passes the user's gate rules, the wall's command-text check and walled roots, then the broker's decision on the bash call it amounts to.

It is judged twice. `rlm.run` refuses a denied check at spawn, before anything is admitted, with the gate's own reason: `the check is refused before it runs on the host: Denied by rule ...`. `rlm.result` judges it again just before it runs, because a rule can be promoted between the two, and holds the result back with `result held back; its check is refused: ...`. An allowed check still runs in the child's cwd, and a red one still holds the result back with its evidence.

The three refusal sentences the gate shares with heartbeat sources no longer say `an exec:// source`, since a spawn check meets them too; they name the command and say it runs later on the host. A gate rule keeps its informed retry: with `gap: once` the same command passes the second time, as it does for a bash call (#1046 stays open for that decision). One feature-ledger row (trigger rules) names the new journey.
