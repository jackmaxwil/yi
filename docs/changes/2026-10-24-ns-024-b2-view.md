This is Bet 2's view (unit B2-view). It adds `yi_tools::view` and the closed list of producers it bounds, `yi_tools::Involuntary`: `Job`, `Traceback`, `ShellCell` and `Check`. Bet 1 adds the child preview and the schema failure. No producer calls the view yet. B2-jobs, B2-cell, B2-kernel-headtail and B2-goal-tail wire it in, and this unit's kill corpus is what lets them open.

`view` runs the foreground bash reducer. When the reduced text and its `[full output: …]` pointer still pass `VIEW_CEILING` (16,384 B, the reducer's own `ERROR_BYTES`), it keeps two thirds of the room from the head and the rest from the tail, where a verdict sits, each end on a line boundary. One row goes between them: `[… K of T bytes kept (VIEW_CEILING 16384); the rest: read <file>]`. The file is the spill the reducer already named, or a new tee of the raw output. A producer with no recovery dir gets a rerun instead. For a job or a check it is `bash (<command>) > view.log 2>&1, then read view.log`, and for a shell cell it is the same command in a `%%bash` cell. For a traceback it is an ipython cell running `traceback.print_exception(sys.last_value)`. That call was run in the real Yi kernel after a recursion error: it prints the traceback in Python's own format (903 B, the repeats collapsed), so it brings back the exception but not IPython's exact bytes.

The column clip lives in the reducer, so foreground bash gets it too. Past the 8,192 B floor, a line longer than 512 chars (`LINE_CLIP`) is clipped with `…`, and one row after the first clipped line counts the chars kept against the chars those lines held. The row points at the full output named below it. A clipped output always keeps a file, even when the clip makes it longer (a 513-char line), because it is lossy either way. A cut capture whose spill is past `SPILL_READ_LIMIT` (4 MiB) used to fall back to numbering the capture without saying why. It now opens with a row saying 0 of that many bytes were read, so omitted-line numbers count the cut capture, and naming the file to read with offset and limit.

`yi_tools::cut` builds every one of these rows: `[… kept of total what (CAP limit); the rest: next]`. Later CAPS units use it for the same three facts. The tests parse it back with `parse_cut`.
