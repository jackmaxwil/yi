A walled session's kernel cells and their `bash()` jobs read no other session's spills or transcripts (Closes #889). The kernel's Seatbelt profile already carried the wall (#911) but not the roots a contained bash call adds for a walled session (#968, #979), so a cell could open any spill under `~/.yi/spills` or `~/.yi/tool-output` and any transcript under `~/.yi/sessions` or the `--session-dir` in use. The profile now denies those roots too, and a later rule reads again the family board and, named per boot and per job since a child's store attaches after its wiring, the session's own spill dir, its transcript and its kernel's state dir: a child's own dir (with its own children's transcripts), a walled root's `kernels/<id>`, never the root's corpus. A spared path that is also a writable root, matched by its resolved spelling, keeps its writes, so the kernel's snapshot and `rlm.put` still land; the own spill dir stays read-only. A spare never beats the wall itself: one under the wall's own `deny_read` is dropped, and a denial at or inside a spare, read or write, is applied after it. No other host-side read a walled kernel can trigger bypasses the walls: `fetch` goes through the walled resolver, the board is read only as regular board files, `plan.op` import is refused to a child's actor, and history search is root-only. Calls that run outside the sandbox still meet the wall only at the tool seam, as a check of the command text that does not cover these roots: a bash call approved to leave, yolo, every call on Linux (where the kernel runs unconfined too), and a heartbeat's `exec://` source, which meets only the permission broker; #1001 carries them.
