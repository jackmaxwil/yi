`yi stats --by plan` counts what the plan engine did. It lists every applied op by kind and by who applied it (the owner, the engine, a child, or an approver standing in for the user), with totals for delegations, worktree acceptances, `done_refused` and retries, and it takes `--since` like the other views. The counts come from two places: the `plan_op` entries in every session file under the sessions directory, children included, and the `ops.jsonl` journals in the project's plans directory. The journals are needed because a session file mirrors only the ops its own engine emitted. The engine's `spawn_intent` and `spawn_result` records and every op the table rejected exist only in the journal, and so does everything the `yi plan` verbs apply. A record found in both places, or in a copied session file, counts once, even though the journal and the session write its keys in different orders. An op the table rejected is its own row, `done (rejected)`, and is never counted as the op it rejected; a refusal by the verifier keeps its kind, `done_refused`, and is what the `doneRefused` total counts. The table shows 40 rows and names how many it cut, and a window with no plan ops says so instead of printing a bare header. It reads the plans directory of the project it runs in (`plans.dir` when set), so another project's plans reach it only through the session files. No role column ships: every spawn is a root spawn today, so the column would hold one value.
