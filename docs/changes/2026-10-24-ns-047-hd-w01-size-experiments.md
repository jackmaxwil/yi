Three size levers that had never been tried on the dist build were measured against the unchanged tree, and none cleared the bar, so no build flag, helper or baseline changes. The bar was fixed before the first build: a lever stays only if it saves at least 65,536 bytes (four 16 KiB pages) and moves startup by no more than 0.3 ms. The unchanged tree builds 8,554,224 bytes.

Turning the machine outliner off with `-C llvm-args=-enable-machine-outliner=never` grows the binary to 9,875,184 bytes, 1,320,960 more: the outlined functions are code the outliner folded out of the call sites, so removing it undoes the saving it makes at `opt-level = "z"`. Forcing unwind tables off with `-C force-unwind-tables=no` is accepted by rustc 1.94 on aarch64-apple-darwin and produces a byte-identical binary, so the 77,008 bytes of `__unwind_info` and 55,144 of `__eh_frame` stay; the Linux binary has its own budget, measured by the forge, and was not measured here. A shared sort helper cannot reach the bar: `cargo bloat` puts all `core::slice::sort` code in `yi_runtime` and `yi_tools` at 82,000 bytes, the helper's reach is the 22 of 62 production call sites that sort strings or small tuples, and replacing exactly those with a 15-line insertion sort, the cheapest stand-in for a helper, saves 33,024 bytes, so a helper that still links one std sort saves less. Replacing all 62 with the same insertion sort saves 82,560, but that stand-in is quadratic and a shared O(n log n) sort was not measured, so that variant stays open with a ceiling of 82,560.

The measurements, the commands and the reasoning are one row of docs/size-ledger.md. Rebuilds of an unchanged tree are byte-reproducible, so one build per lever replaces the three averaged builds the plan named; the unwind build, an independent rebuild with different flags that matched the control byte for byte, is the proof. Startup was not the deciding arm, because no lever cleared the size bar. Unit: HD-W01-size-experiments.
