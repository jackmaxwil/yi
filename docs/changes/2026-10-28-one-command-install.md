Yi installs with one command: `curl -fsSL https://raw.githubusercontent.com/jackmaxwil/yi/main/scripts/install.sh | bash`. Piped into bash, `scripts/install.sh` names this machine's target, reads the release's `SHA256SUMS`, downloads the archive it lists, and installs it only when the archive's sha256 matches; a mismatch exits 1 with `nothing installed`. With `ssh-keygen` on PATH it then checks the archive's `.sig` against the release key it embeds (the one line of `allowed_signers`, which `--help` prints), refuses a bad signature with `nothing installed`, and says when the release has no `.sig` or the host no `ssh-keygen`. Run from an unpacked release it installs that tree as before. `YI_VERSION` picks a release, `YI_RELEASE_BASE` reads one from elsewhere (an `https://` or `file://` directory), and `--dry-run` and `--help` change nothing. It is a bash twin of `yi update`'s install half because no `yi` exists yet to run; it unpacks with the system `tar`, which strips a leading `/` and refuses a `..` member, and the digest it checks is the trust root, as a hostile host could serve any binary at all. `just publish` folds the archives' `.sha256` files into the `SHA256SUMS` a release carries and refuses an archive with no `.sig`; `scripts/package.sh` removes an archive it could not sign. The GitHub release is `scripts/mirror/publish.sh`, an owner-run tool that never runs in CI: it builds a clone of the mirror's tag, signs it, refuses an archive in which any deny.txt estate pattern matches, and uploads the archive, `.sha256`, `.sig` and `SHA256SUMS` with `gh release create --verify-tag`. The mirror now pushes each forge `v*` tag on main at its rewritten commit, on main pushes and on tag pushes, checked by `scripts/mirror/sync_test.sh` in the mirror job before every push.
