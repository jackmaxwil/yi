The dist binary no longer embeds the checkout path. The kernel's last-resort python root was the compile-time manifest directory; it is now `/nonexistent/yi/python`, which fails closed instead of loading code from the cwd. The binary-size gate fails when `target/dist/yi` contains the checkout, cargo registry or rustup toolchain path (also resolved), so a path that leaks back in is red on its own reason. The dist build and the gate derive those cargo and rustup roots from one helper. Two offline dist builds of this tree from checkout paths of different lengths both measured 8,686,704 bytes, so checkout path length did not move the measured size; this does not explain the original three-worktree spread or claim byte-identical binaries. A byte scan of a third dist build of this tree found none of the checkout, cargo-registry, rustup-toolchain, cargo-target, home or tmp paths anywhere in the binary (the cargo-target path is outside the gate's roots and was scanned too); the only build-tree path it carries is the fixed `/nonexistent/yi/python` constant, so this build holds no second variable-length path source outside the roots the leak gate checks. The baseline tracks the measured fixed size, not variance: at the old 8,670,192 the fixed measurement 8,686,704 is already 128 bytes over budget plus jitter (8,686,576), so holding it would leave the gate permanently red, and any size slack a leaked path needs is denied by the leak check, which fails on the path itself before the size is read. What would settle the three-worktree spread if it stays unexplained: rebuild the same tree in the three original worktrees and read the leak check's verdict, where red names the path it found and a spread with no leak points at a toolchain or dependency difference the path roots cannot see. The original embedded path was found by running `strings` on a dist build. Until the original spread is explained, a size failure outside the scanned paths is a finding, not a ratchet case.
