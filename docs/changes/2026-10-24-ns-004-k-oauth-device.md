A login profile at `~/.yi/oauth/<provider>.json` may now be `kind: "device-code"`, and `yi login <provider>` then runs the RFC 8628 device flow (unit K-oauth-device). Yi posts the profile's `client_id` to its `device_authorization` endpoint, opens the verification page (or prints it with `--no-browser`) and shows the user code. It then polls the `token` endpoint at the server's interval, five seconds slower after each `slow_down`. The login ends on a token, on `access_denied`, on `expired_token`, on a 5xx or any other error code (quoting the server's body, JSON or not), or when `expires_in` (at most 15 minutes) has been waited out; an expired code names `yi login <provider>` as the way to start again. The token is stored and refreshed like every OAuth login, under the same cross-process lock, so a rotated refresh token is what gets saved. A device-code profile that sets a key only the loopback login reads, such as `client_secret` or `callback_port`, is refused by name, and so is an oauth-code profile that sets `device_authorization`. The verification page is opened only when it is https or loopback, and a user code or verification URI carrying a control character is refused rather than printed. An api-key profile that sets `device_authorization` or `api_base` is refused by name. A profile may also name the `api_base` its token serves, which the Kimi catalog reads next. A token response whose `expires_in` is a float such as `900.0` now expires; before, it was stored as a token that never expires. Yi still ships no client id, endpoint or wire identity (D191 holds); docs/examples/oauth-device-profile.json is the template.
