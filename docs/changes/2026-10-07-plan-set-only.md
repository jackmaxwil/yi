The plan tool now shows the model three ops: `set`, `view` and `accepted_by_user` (Refs #1077). Every other change is a row's state in `set`: `failed` with its `cause`, `dropped`, `pending` or `running` to reopen a failed or blocked row, and a row's own `todos` as the sub-steps it splits into. A `set` keeps every row it does not name, so a call made from a stale view never deletes one; a row leaves by state `dropped`, or by a struck `- [-]` line in a checklist. Calls written for the older ops still land. A call that carries no rows is refused again and names the call that would land, `{"op":"set","todos":[{"label":"…","state":"done"}]}`: reading it as a view of the plan let one model repeat it eleven times while every call counted as a success.

When a new plan takes the session's todo list, the rows the finished plan had taken from that list come back to it with their final state, instead of vanishing. The surface eval counts the two scenarios that ask the model to provoke refusals on a line of their own, beside the gate, and takes `EVAL_ROUTING` as the other eval runners do; the plan-tool gate runs with the InferenceNet upstream ruled out, which delivered `set` calls with their rows missing from the raw stream.

A `set` on a plan that has finished reopens it with the rows it names, instead of refusing; the plan is active again while any row is open. A question to the user with one or two options is asked as an open question, with a note, instead of refused. A todo-tool `block` on a row the plan owns is carried to the plan tool, as `done` already was.
