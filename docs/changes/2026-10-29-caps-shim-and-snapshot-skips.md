The runtime's two remaining silent cuts are named (unit CAPS-runtime, finishing what 0.753.0 left open on #1487). A `rlm.find_models` search that matched more than `limit` already produced a `[… kept of total matching models (limit N); the rest: await rlm.find_models("", limit=T)]` row in the host reply, and the `rlm` shim read only `models`, so the row never reached a cell and the model saw a short list with nothing to say it was short. The shim prints the row now, and its docstring says the list it returns is at most the `limit` asked for.

A variable the snapshot left out came back as silence. The snapshot has always counted its skips (`KernelSnapshotResult.skipped`: over the 16 MiB per-variable cap, over the aggregate cap, or unpicklable), but only the snapshot's own marker line saw them; the resume read an index that no longer held the name and said nothing, so a revived kernel's notice claimed a namespace it did not have. The skip list now rides the index itself under a `_skips` key — the loops skip every name starting with `_`, so it cannot collide with a variable, and one write commits the names and the skips together instead of a second file that could describe a snapshot that never landed. The restore normalises each entry to `{name, reason}` with a string reason, so a stored shape cannot make the marker line undecodable and blank the revive notice, then appends those names to the `failed` names it reports. The notice names each one, cut at `RESTORE_FAILED_SHOWN`, and always ends by naming `_yi_restore_failures`, the restored kernel list that holds every failure with its reason; the cut row's continuation is that bare name, so no builtin a user shadowed is resolved.

No type changed: `KernelSnapshotSkip` already says "one name the snapshot/restore helpers could not process, with a short reason", so a name the snapshot skipped is a name restore did not produce.
Risk and rollback: the restore reads no new file; the skip list is a `_skips` key inside `kernel-state.dill`, and the notice prints the names without their reasons, pointing at `_yi_restore_failures` for those. A binary from before this change reads that key as a blob, so its first resume names a phantom `_skips` (TypeError) and loses the real skip list. Delete `kernel-state.dill` before reverting, or accept that one report until the reverted binary writes its next snapshot, which drops the key; a snapshot taken before reverting does not help, since this version always writes `_skips`.
