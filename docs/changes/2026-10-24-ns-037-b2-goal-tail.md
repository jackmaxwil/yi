This is Bet 2's goal tail (unit B2-goal-tail). A failed check used to reach the model as the last 2,000 chars of its output with nothing saying it was a tail. That tail now goes through the view B2-view added, `yi_tools::view`, and `output_tail` is gone. One function, `check_view` in `goal/mod.rs`, takes the check's command and its capture and returns the view's text. Past `VIEW_CEILING` (16,384 B) the text is the head, one row and the tail, and the row names kept over total, the cap and the rerun that writes the rest to a file: `bash (<command>) > view.log 2>&1, then read view.log`. A check keeps no spill, so the rerun is the recovery. Output under the ceiling now arrives whole where it used to be cut at 2,000 chars.

Three places print a failed check, and all three call `check_view`: the goal gate (`run_check`), a checker item's refused detail (`verdict_of` in `plan/verify.rs`) and the `exec://` source of a heartbeat (`schedule/adapter.rs`). The pass evidence of `run_cmd_said` keeps its own 300-char tail and its own loud row, now taken from the raw streams.

A check's capture is cut at `OUTPUT_CAP` (30,000 B a stream) before the view sees it, so the view's total can be smaller than what the check printed. `check_view` appends the capture's own cut row after the view's, and both capture sites name `OUTPUT_CAP` in place of the literal, so that row quotes the real cap. A 32,955 B `pytest -v` run reads `[… 16074 of 30038 bytes kept (VIEW_CEILING 16384); the rest: bash (…) > view.log 2>&1, then read view.log]` and `[capture cut: kept 30000 of 32955 bytes (OUTPUT_CAP 30000 per stream); no file kept the rest]`.

The `exec://` source needed one more guard. A channel refuses a message past `MESSAGE_MAX_BYTES` (16,384 B) whole, with its data set to null, so a red level with a ceiling-sized view in it would stop matching an `ok=false` filter and the todo that filter makes would never be created. When the level and its output would serialize past the cap, the message keeps `ok` and `exit`, and its output is one row: `[… 0 of N bytes kept (MESSAGE_MAX_BYTES 16384); the rest: bash (<command>) > exec.log 2>&1, then read exec.log]`. The same ceiling value on both sides is a coincidence the view cannot see. A `ceiling` argument on `view`, set from the channel's cap, would keep the tail in this message too, and belongs to B2-view's owner.

The behavior fixture `done-claim-red-check-refused` is unchanged: its check is `false`, which prints nothing, and its assertions name only `completion rejected` and the exit line.
