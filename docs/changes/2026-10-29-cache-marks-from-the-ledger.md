A route's cache marks now follow what its own session shows (Closes #748). Three behaviours build on the ledger fold D315 landed, and none of them asks a model.

The upstream: OpenRouter may answer a conversation on a different host between two requests, and an entry the old host wrote is then unreadable there. The fold already names that miss (`upstream switch`) and never counted it. Two of them inside thirty minutes now pin the host that last read the entry: `ProviderStream` sends it as `provider.order` on the next request, by its OpenRouter slug, with fallbacks still allowed, so a name no host matches costs the preference and nothing else. The pin lapses after an hour and the switch count restarts, so a route that keeps moving re-pins and one that settles keeps its entry.

The tail mark: a request's own tail is where the next request reads from, and a route that wrote it and read nothing back for four consecutive unexplained requests is writing a mark nothing reads. The fold stops the moving tail for an hour and keeps every mark before it, the previous tail included, since those are what the next request does read. After the hour the mark is written once more: four more zero-read writes suspend it again, a read ends the run and the mark stays.

The refusal: a provider that does not know a cache field answers 400 rather than ignoring it. A 400 whose body names one of `cache_control`, `cache_ttl`, `prompt_cache_key`, `prompt_cache_retention`, `session_id` or `cache` is now asked again once with every cache field removed from the body, and the reply records the field the route refused as a `cache_stripped` diagnostic, so the ledger says the request went out without its marks. A 400 that names none of them is reported unchanged, never resent: the same body would be refused the same way.

The previous tail needed no switch of its own: D295's build already sends it on every loop request, so the escalation it was meant to gate is unconditional.
