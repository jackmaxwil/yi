A plan todo whose contract keeps failing now has to change course before it is claimed again. After two red verdicts on one attempt, the next `done` is refused before its check runs, and the refusal names the two ways out: `split` the todo into one to four children, which the parent then waits for, or `append` todos with `for_task` naming it. Either buys one claim. The third red blocks the todo on the user as before, and the user's unblock now buys one more claim instead of leaving the todo pending with every later `done` refused. A `split` or targeted `append` that would buy nothing is refused with the rung it met. `plan.done_refusal_cap` moves both gated rungs.

The cap's block asks the user a question (try it once more, accept it, drop it). Their reply in the chat, picked up by the next `unblock`, buys one claim; nothing else does (where nobody can reply, as in `yi plan`, the refusal says to drop it or accept it from a session), and a `fail` then `retry` after the cap starts the new attempt at the count the old one reached.

`split` parses on every surface (`{"op": "split", "label": L, "subtasks": [{"title", "acceptance", "contract"}]}`) but is not in the tool schema, so the request does not grow; the refusal carries the literal call, and the plan skill and the tool guide (`yi://tools/plan`) name it. A subtask key nothing reads is refused at the tool, so a misspelled `contract` never lands a child on the unverified path, while the journaled shape stays lenient.

`readmit` and `split_parent` live in `Todo.extra` until `doc.rs` splits at a seam and types them (#2157).
