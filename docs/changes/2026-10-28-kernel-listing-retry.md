The kernel's namespace query answers on a second attempt instead of reporting no names. `Snapshot::list_namespace_names` is a read of a live namespace, and a listing that arrives while the kernel is busy spends its five-second budget waiting for the queue rather than listing: it came back empty, the caller read that as "this kernel has no names", and gate run #94 reddened `yi-kernel::kernel_e2e prune_removes_oversized_variables_and_list_names_reports` on a tree that touched nothing under `crates/kernel`. It now makes up to two bounded attempts under one deadline of `LISTING_ATTEMPTS` times the 5 s listing budget, each attempt capped at that budget, and only a kernel that misses both reports no names. Every attempt's reason reaches the kernel diagnostic, tagged with its attempt, so a first-attempt timeout and a different second-attempt failure both survive to the line; an aborted attempt that carried no stderr or error is named for what it is, a timeout spent waiting on the execution queue, rather than printing an empty detail. Cost on the failure path: a dispatched attempt ends when its abort fires and `resolve_active` frees the slot, which is `KERNEL_ABORT_GRACE_MS` (1 s) later, so a hung kernel costs a caller up to 10 s of attempt budgets plus one grace against the 5 s plus grace it cost before. That stall is not rare: `crates/runtime/src/kernel.rs` runs the listing inline after every non-aborted user cell, so a contended kernel now delays each cell's notes by the same doubled wait, and the listing's 2.8-3.3 ms is a per-cell cost, not one a question pays once. The retry starts after the first attempt's abort has interrupted the stalled cell, so it measures a settled kernel when the slot did free; an attempt that finds a slot still held pays that queue wait inside its own budget. Run #95, the identical tree, was green, which is what made this a gate flake rather than a regression.
