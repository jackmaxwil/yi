A headless `yi ask` that needed an approval nobody could give ended its tool call with `Permission required but no interactive surface is available`, exited 0, and named no way through, so a caller could not tell a refusal from an answer. `permissions.allow` in the config takes entries written `TOOL PATTERN` (`bash cargo test*`), a glob over the call, and every session builder now passes them to the broker as allow rules; the CLI passed none before, so no config rule ever reached a run. The refusal's tool result ends with the entry that allows exactly that call, ready to paste as JSON, with the call's own `*` and `[` escaped so it matches nothing else. A headless `ask` whose last tool call was refused exits 4, prints the denied tool, arguments and reason on stderr, and under `--json` ends with `{"type":"denied","tool","args","reason"}`; a denial the model got past with a later call that ran does not count, and an interactive run is unchanged. An entry with no pattern, or a pattern that is not a glob, exits 2 before the model runs. Under `--eval` a `no_answer` line may follow the `denied` line.

No `--allow RULE` flag: a rule typed on the command line skips the policy as `--yolo` does, and the config is where a standing rule belongs. A refusal the sandbox causes (a path it keeps closed, a nested sandbox) still says to rerun with `--yolo`, since no allow rule changes what the sandbox does.
