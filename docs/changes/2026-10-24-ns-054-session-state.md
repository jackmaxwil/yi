A forked child is seeded the way compaction would cut the parent. `fork=N` used to count every user-role message as a turn, host notices included, so a parent whose last messages were lifecycle notices handed a `fork=2` child two notices and none of the request. It now counts only messages whose attribution reads as typed. The seed is walked newest first with compaction's bytes/3 estimator against the child's window less the compaction reserve, and it opens at the first cut point that fits (`compaction::fitting_start`), so a budget that cut right after a tool call no longer opens the seed on that call's orphaned result. A seed the budget cut opens on a notice row naming kept of total messages, the token budget and `history://parent/since/0` for the rest, which also means a cut seed never opens on an assistant turn. The seed is appended to the child's session file before it is set in memory, as a partition is, so a service that crashes and is respawned from its kept transcript still opens on it. `seed_for_fork` moved from `subagent.rs` to `subagent/reader.rs`, beside `reader::seed`, which now takes the fork seed and the partition together.

A resumed session's system prompt is rebuilt from the running build. The `ext_state` snapshot used to hold every slot's text and the yard, and `Host::start` replaced the whole slot table with it, so a session resumed with `--mode yolo` was still told the mode it was started in, and its identity and doctrine were the build's that wrote the file. The snapshot is now version 2, written as a new custom entry type, `ext_state2`: a slot the build attached before the session started (identity, doctrine, the permission mode, a user system prompt, a schema) is stored as rank, name, SHA-256 and byte size only; a slot an extension attached (a language pack, the orchestrate protocol, the skill catalog, a plugin card) and the yard keep their text, and a slot attached after the first request is marked `late`. The new type is what keeps old binaries whole: they read only `ext_state`, so a rollback or a stale daemon that resumes a v2 session keeps its own build slots (the installed 0.525.0 binary, resuming one, wrote a v1 row carrying its identity, doctrine and mode), where a v2 row under the old type would have replaced its table with the extension slots alone. On resume `Host::start` reads the newest of either type, keeps the build's slots and re-attaches each recorded slot with text that the build lacks; a slot marked late goes back into the late set, out of the base prompt, since the transcript already carries its fragment and a compaction delivers it again. The session start then re-attaches what the extensions produce now. A v1 snapshot, which carries text for every slot, restores through the same rule, so an old session resumes with the current doctrine and its recorded extension slots. A snapshot is appended only when an extension changes the table, so a resume under an unchanged build writes none and the cache-miss fold sees no system move. A resume under the same build and mode sends byte-identical system bytes, a late attach before the resume included; one after an upgrade costs one cache miss, as before. `evals/prefix_capture.py` reads both types and takes a hash-only slot's size from its `bytes`.

`AgentSession::system_prompt` no longer freezes the prompt; only the loop's read does. `compact_now` read it before the first prompt, which froze a prompt the session start had not yet given its project instructions (a debug build panicked on the external attach that followed; a release build sent the first request without AGENTS.md). The D310 byte check in `session/run.rs` and its `first_system_prompt` field are now compiled into debug builds only.

The environment block runs `git status` once per change instead of once per request. `environment::GitSummary` holds the last branch and counts behind the session's event stream: it reads again after `AgentStart` (a run's start) or a `ToolExecutionEnd` from `bash`, `edit`, `write` or `ipython`, and a receiver that lagged the stream reads again too. Every request of a run reads the same cache, the last-word and claim re-drives at a stop included, so a ten-request run that only reads runs `git status` once where it ran it ten times. The lock is held across the read, so sixteen readers at once run git once. The cache is keyed on events, not timestamps: an edit that leaves a file's mtime as it was still shows at the next request. A change made outside Yi in the middle of a run shows at the next run's start; `grep` with `apply` writes the tree without moving the counts until then. `tracked` and `branch_diff`, the review pane's git reads that ACP serves as `_yi/tracked` and `_yi/branch_diff`, moved from `environment` to a `review_git` module.

Reclaim no longer parses every read, edit and write result on every request. Which files a result's `[path#TAG]` headers name is memoised per session in `reclaim::Sections`, keyed by a hash of the result's text and never by its call id, since leaked calls reuse ids; the lock is held across a parse, so sixteen readers of one new result parse it once, and an edited text is a new key. Measured by the `reclaim.view` trace span over the largest recorded session (`01a0d6e4`, 12 requests, ten reads) replayed 200 times in a release build, a request's reclaim falls from 87.0 µs to 37.1 µs on the mean (57%), with every request's bytes after reclaim identical; the pre-registered bar was 50%. `FetchLog` writes a `fetch` session row only when an address's hash moved, so a file re-read at the same hash adds no row; the in-memory log still keeps the latest record per address.

The claims and claim-redrive halves of this unit were not built. `session_claims` re-scans the branch on each list change and the redrive re-reads the session at each clean stop; scanning only the entries since the last list change or the current prompt cycle changes what they report (evidence recorded before the previous list change, a figure printed in an earlier cycle), and the exact incremental form needs a per-session cache whose only home, `TodoStore` in `todo/mod.rs`, has no lines left under its 1,200-line ceiling once its planned editors land.
