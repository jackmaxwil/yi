A resumed session starts from its ledger, not from zero (Closes #1028, Closes #1029). Restarting `yi serve` and reopening a session that had spent $86 showed $5.72: the status row's dollars and its `N% cached` were sums of the replies this client had watched live, and a replay fed them nothing. The session store already folds every reply and every finished child's usage record into `SessionStats`; a root's `_yi/replay` now carries those totals as `stats` (with `unknownUsage` when a reply came back without usage, so the row reads `≥$86.20`), the console sets its row from them, and the solo TUI reads them from its store through `SessionPort::ledger`. A second replay of the same session (a rewind, a reconnect) sets the figures again rather than adding to them, and live replies still add on top. In the runtime, the cache TTL tracker and the spend alarm were the same defect: both counted from process start, so a session that had learned to write its history for an hour went back to five minutes after every resume, and `spend.alertTokens` restarted at zero. `AgentSession::on_attach` registers a fold that runs over the branch and totals of every store as it attaches, before the first request; the tracker folds the stored replies (and drops a notice the last process already showed), hands its estimate to the provider, and the spend alarm starts from the ledger's token total with the crossings below it already announced; it seeds only when the attached store is another session's (a resume, `/new`, an rpc switch or fork), since a rewind or branch summary re-attaches the same session mid-process, where the ledger already holds a finished child that the host can publish again and the live counts are already right. The S2 slice of #748 only: the adaptive-TTL controller stays open there.
