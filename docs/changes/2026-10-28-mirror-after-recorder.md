decision: a newer push to main cancels the mirror run an older one started, instead of leaving both runs to race the tip guard | the recorder's commit now starts a mirror run of its own, so one merge can have two runs, and the older finishing last would force older history over the newer push | delete the concurrency block from mirror.yml

The mirror runs for the commit that leaves main final. The recorder's push carried `[skip ci]`, so the forge started no workflow for it: the merge's own mirror run cloned main before that commit existed, met its tip guard with the forge's `main` moved on ("the newer run pushes, this one stops"), and the record commit was never mirrored at all. The keyword is gone. The two lanes a docs commit has nothing to run, `postmerge` and `warm`, skip a commit authored by `yi-ci` instead, so a recorder push buys one mirror run and no second live suite. `mirror.yml` gains a concurrency group that cancels a superseded run, so when a record commit lands while the merge's mirror run is still working, the newer run pushes and the older one never gets to force older history; `scripts/mirror/sync.sh`'s tip guard stays as the backstop for the window between a run's check and its push. A `v*` tag needs no dispatch to reach GitHub either: `sync.sh` pushes every tag on main at the commit filter-repo rewrote it to, and the recorder's push is now the main run that does it. `scripts/guardrails/check_workflows.py` refuses any commit message in a workflow that carries a skip keyword, naming the runs it silences.
