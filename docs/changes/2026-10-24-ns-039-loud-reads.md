This is Bet 2's loud-caps part of Yi's next shape, one bundle of two units: CAPS-context-tools and OUT-read-grep-bytes.

CAPS-context-tools. `yi_tools::cut_row` is public (it came with CAPS-runtime), so a crate that holds a cap builds the same `[… kept of total what (CAP limit); the rest: next]` row the reducer does. A context source over its byte budget ends in that row, naming the budget, instead of `[... truncated: N bytes over budget ...]`. `fit` takes the call that gets the rest from its caller: `read AGENTS.md in full` for an instruction file, `read("yi://skills/<name>") for one skill` for the catalog's fallback, and `await memory.search("words")` for the memory block. The compaction view says how many outstanding errors the 12-row cap dropped. A malformed edit header echoes at most 120 chars of the line and says how many it held. A default `read` window cut at 2,000 lines names `READ_LINE_CAP`, and `get_context` says its skeleton scan stopped at 2,000 source files. The 24-range `EARLIER_CAP` and the 160-char brief cuts in the same view are left alone: the earlier ranges are carried from one compaction to the next, so a row there needs a count the persisted view does not hold.

OUT-read-grep-bytes. An unpaged `read local://<file>` keeps its first 51,200 bytes on a char boundary and ends in the row a history listing gets, naming kept of total, the cap and the offset that reads the rest. A window the model asked for (`offset` or `limit`) is never cut. A grep page stops between hits once its rows hold `PAGE_BYTES` (51,200), counting each row's path and line number, and its continuation row names the cap that cut the page (`PAGE_BYTES`, `PAGE_CAP` or `BLOCK_PAGE_CAP`) beside the offset. One hit's window may pass the cap, so a page always advances, and a block hit larger than the cap is still returned whole.
