This PR makes the plan and memory journals cheap to read and fixes three memory faults, in five units, in commit order: HB-plan-read-cache, H41-journal-move, H41-journal-tail-append, H41-memory-guards and H41-memory-list-readonly.

HB-plan-read-cache. `PlanStore::read` and recovery's `reconstruct` read, verified and reduced the whole `ops.jsonl` on every call, so one `set` on a thirty-todo, two-hundred-record plan reduced its journal seven times, and sixteen first reads of one journal reduced it sixteen times. `plan::cache` holds the reduced journal per path and hands it back while the file's device, inode, length, mtime and last line are what they were; the stamp is taken before the read, so a write racing a read can only make the next reader reduce again. Its stamp and slot are the same `file_cache` primitive used by the history corpus and schedule's zone cache, so replacement and restored-metadata invalidation live in one place. A damaged chain is refused there, as both readers did, and a torn tail is never held. The plan schema compiles once instead of on every checkpoint read. `reduce` now records a `plan.reduce` span under `YI_TRACE`, which the tests count: one `set` reduces twice (load, then the read of what it committed) and sixteen readers reduce once. The constant-churn wait test accepts a quiet-window unblock before the two-second budget but refuses a success after it, so faster cached reads cannot turn its oracle flaky.

H41-journal-move. `plan/journal.rs` (the hash-chained `Journal`, `Fs`, `RealFs`, `JournalError`, `Reading` and `Lines`) is the primitive under both the plan store and the memory store, so it moves to `crate::journal` with no change in behaviour; every user takes the new path.

H41-journal-tail-append. `memory::journal::Journal::append` replayed the whole `ops.jsonl`, parsing and re-verifying every record, to learn the previous digest, and `mark_read` appends a record on every `memory.read`, so each read cost more than the last: at 50,000 records one read took 1.24 s against 53 ms at 1,000 in a debug build. The append now reads the last line with `Journal::tail` and chains from it; when the file does not end in one whole record (a torn tail, an over-cap run, a line that is not a record) it takes the full replay as before, which sets a torn tail aside. At 50,000 records a read takes what it takes at 1,000. A chain broken in the middle is no longer noticed by an append, which never acted on it; `yi memory rebuild` replays the chain whole and names the break, as before. No retention policy is added: the append alone measured 5.1 to 5.3 ms at 50,000 records in a debug test build under parallel builds, flat in the journal's length, and most of it is the `sync_data` commit point.

H41-memory-guards. `key_run` found its prefix anywhere in a token, so `disk-backed-storage-layer` and `risk-based-queue-management` were refused as API keys: each holds `sk-` with sixteen key characters after it. A key now starts at a token edge (the token's start, or after a character that is not a letter or digit) and its run holds a digit, which every provider key format carries. `sk-ant-api03-`, `sk-proj-`, `ghp_` and `AKIA` keys are still refused at a token's start and after `=`, a quote, a bracket and a space; the same run glued to a letter is a word. The loop guard refused any `<memory`, which no code writes since D278 struck D170's anchors, so a note that quotes one is kept; the yard fence `<<<yi-external` is still refused. docs/memory.md states both guards.

H41-memory-list-readonly. `yi memory list` printed its summary through the session-start block, which reconciles each store first: it took the store lock, journaled `adopt` and `edit` records into `ops.jsonl`, copied a hand-written note into `objects/` and rewrote `MEMORY.md`. The block now takes the index as a function: the session start passes `Store::reconcile` as before, and `yi memory list` passes `Store::indexed`, the index reconcile would write, read without writing, so a list changes no file and a hand edit is journaled at the next session start. A hand-written note is still listed, since the list reads the note files themselves.
