The kernel's environment was fixed when it booted, so a plugin installed by `yi plugin add` mid-session reached the bash tool and `rlm.bash` (which build PATH per command) but not `!` lines, `%%bash` or `subprocess` in a cell. Before each cell the kernel service compares the installed program plugins with the directories it last put on the kernel's PATH and, when they differ, runs an internal cell that leads PATH with the installed directories and drops the ones a `yi plugin remove` took away, leaving every other entry alone, so a directory a cell added to PATH survives the refresh and a removal reaches the kernel instead of waiting for a restart. A kernel whose plugin set has not changed since boot is left alone. The journey test `kernel_lane::a_plugin_added_after_the_kernel_booted_is_on_the_next_cells_path` boots a kernel, seeds a PATH entry from a cell, publishes a plugin program, finds it with `!which` and `subprocess`, and checks the entry and the removal both landed on the kernel's PATH.
