This is the usage fold (unit HA-TOK-fold). A goal's token budget stopped counting fresh tokens once a conversation had a long cached prefix. The goal subtracted a reply's cache reads from its input, but the providers already report `Usage.input` without them (the Anthropic mapper copies `input_tokens`, which leaves out cached and cache-written tokens, and the OpenAI mappers take the cached tokens off the prompt count themselves). With 500 fresh input tokens and 9,000 cache reads, the subtraction went negative, was clamped to zero, and the reply counted for its 300 output tokens alone. A goal with a budget of 1,000 tokens needed four such replies to cross it instead of two, and the longer the cached prefix, the later it crossed.

`Usage` now has two named folds in `yi-types`, so there is one place that says how a usage block reads as tokens. `fresh` is input plus cache writes plus output, what the reply newly cost, and the goal's accounting reads it where it used to call its own `usage_delta`, which is gone. `context` is input plus cache reads plus cache writes, what the request held whether it came from cache or not; nothing reads it yet, and the child and live-context units that follow name it as their input. Each part is clamped at zero before the sum and the sum saturates, because a live usage chunk can map to a negative `input`: an OpenAI-shaped upstream whose `prompt_tokens` is below the cache counts it reports beside it, which the mapper subtracts from the prompt. A negative part must not take a real count with it.

No wire shape moves: `Usage` and `Goal` serialize as before, and a goal's stored `tokens_used` is only counted differently from here on. A goal stored by an older build keeps the lower count it had.

One producer is not net of cache reads: the OpenRouter generation record that settles a cut turn stores the whole prompt in `input` and the cached part beside it in `cache_read`. That usage reaches the store's `settled` rows and, for a child, its parent's last message through the settle hook the child is wired with, but never the goal, which folds only the live reply. A later fold over those rows (the child-token and stats units) has to take `cache_read` off `input` first, or the record should store it net, as the stream mappers do.
