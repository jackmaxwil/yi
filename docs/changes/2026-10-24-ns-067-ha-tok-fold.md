This is the usage fold (unit HA-TOK-fold). A goal's token budget stopped counting fresh tokens once a conversation had a long cached prefix. The goal subtracted a reply's cache reads from its input, but the providers already report `Usage.input` without them (the Anthropic mapper copies `input_tokens`, which leaves out cached and cache-written tokens, and the OpenAI mappers take the cached tokens off the prompt count themselves). With 500 fresh input tokens and 9,000 cache reads, the subtraction went negative, was clamped to zero, and the reply counted for its 300 output tokens alone. A goal with a budget of 1,000 tokens needed four such replies to cross it instead of two, and the longer the cached prefix, the later it crossed.

`Usage` now has two named folds in `yi-types`, so there is one place that says how a usage block reads as tokens. `fresh` is input plus cache writes plus output, what the reply newly cost, and the goal's accounting reads it where it used to call its own `usage_delta`, which is gone. `context` is input plus cache reads plus cache writes, what the request held whether it came from cache or not; nothing reads it yet, and the child and live-context units that follow name it as their input. Each part is clamped at zero before the sum and the sum saturates, because Pi v4 session files carry negative token parts in usage adjustment records and a `-1` sentinel must not take a real count with it.

No wire shape moves: `Usage` and `Goal` serialize as before, and a goal's stored `tokens_used` is only counted differently from here on. A goal stored by an older build keeps the lower count it had.
