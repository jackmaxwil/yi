A model gateway that speaks the OpenAI chat-completions API is now a provider of its own. `providers.<id>` in `~/.yi/config.json` speaks chat completions and names its `baseUrl`, where its key is (`apiKeyEnv`, else a literal `apiKey` for a gateway placeholder that is not a secret, else the yi-oauth token at `~/.yi/providers/tokens/<id>.json`) and its `models`, each needing only an `id`, with `name`, `reasoning`, `input`, `contextWindow`, `maxTokens` and `cost` optional. A model of one is addressed `<id>/<model>` like any other. The declared models merge after the bundled catalog and the refreshed cache, so `yi catalog refresh` neither rewrites nor drops them and never fetches a custom provider. Requests go through the OpenAI completions adapter at the declared base URL with plain `max_tokens` and none of OpenAI's own fields. An id a built-in provider, `laya` or `faux` already holds refuses when the config loads, naming the id. A provider with no key anywhere is refused before any request, naming the variable that would supply one; a real key belongs in that variable, never in `config.json`. The block is read once per process, so the settings row says an edit takes hold after a restart. `yi doctor` has a `providers` row naming each one, its model count and base URL, and where its key resolved, naming the token file a store key came from.
