A walled session's commands no longer leave the sandbox where one exists, the ones that run on the host meet the wall's roots, and its kernel never runs unconfined (Closes #1001). On macOS, a walled session's bash call that would run outside the sandbox (network, an install, a credential store, or the retry of a refusal that named no path) is refused before anyone is asked, even when a rule allows it or someone would approve it; its `exec://` sources, which only ever run on the host, are refused too. Yolo is the user's own choice and still runs them on the host. Where a walled call does run on the host, under yolo or on Linux, and for a heartbeat's `exec://` source, which was judged only by the permission broker, the wall's command-text check now also covers the spill roots and session stores: a command naming one or a directory above it, quoted, escaped, after a `:` or `@`, glued to a flag, or by `~`, `$HOME`, a glob, a link or `..` resolved from the session's directory and from every `cd` target the command names, is refused, and its own spill dir and transcript still read; a wall naming a folder above them drops those spares here too. That check is text only: variables, `$(…)`, a `cd` it cannot read and paths a program builds pass it, so on Linux and under yolo it stops an honest agent and no more. Contained calls meet Seatbelt alone, which no longer spares the session's own spill dir or transcript when the wall itself names a folder above them. On Linux a walled session's kernel is refused before it boots, with a message naming the missing sandbox, so a juror or any role-root walled child has no ipython there; readers and workers never had it, and read, grep and bash still work.
