`rlm.merge_worktree` now says what a hand-back left behind and what to call next. When the parent checkout held uncommitted edits to a file the child also changed, the merge is published by moving the branch ref alone and the edited files stay as they are on disk. The reply said only `merged: true`, so the next commit of those files silently undid the child's change. It now carries `kept_yours`, the paths whose edits stayed, and one sentence saying that `git diff HEAD` shows the child's change as removed there and that `git show HEAD:<path>` is the merged version to fold the edits into. A kept path that `git show` cannot find in `HEAD` is one the child deleted, and it is untracked in the checkout. A fast-forward reply is unchanged and carries neither key.

A conflict reply (`merged: false`) now carries a `next` sentence. The child's lane is already released and its work is kept on its branch, which the reply names: `git merge <branch>` in the parent checkout stops at the conflicts listed, and `git branch -D <branch>` drops the work. `rlm.discard_worktree` is not named because it no longer reaches the child after a conflict: it answers that the child has no worktree.
