This PR carries two units of Yi's next shape, E-ci-live-weekly and HD-G02-surface-trims.

The paid weekly live job, `live-weekly`, moves out of `.forgejo/workflows/tracking-hygiene.yml` into its own `.forgejo/workflows/live-weekly.yml`. The job is the three flash runs, the Anthropic run and the OpenAI run, with its 40 minute timeout, rust-cache key and per-secret skips unchanged. The new workflow keeps the weekly Monday 05:17 UTC trigger the job already ran on and adds `workflow_dispatch`, which tracking-hygiene already had; the trigger now exists in each file for its own jobs only, so the paid job runs once a week. tracking-hygiene.yml keeps its milestone, hygiene and catalog-drift jobs and its header about milestone dates. The one-routing-pin check in `evals/selftest.py` (the ledger judges a PR's live run by main's runs of the same routing) now reads `live-weekly.yml` where it read tracking-hygiene.yml, since the `EVAL_ROUTING` pin moved with the job. docs/FORGE.md lists the new file and names it as the reader of the three provider keys.

A PR whose only change to the tool surface removes words no longer owes a Claims ledger. `scripts/guardrails/baselines/tool_surface.json` now keeps each key's text beside its sha256, and `surface_diff` in `scripts/pr_body.py` splits a changed key into `grew` and `trimmed`: a key is trimmed when its byte count fell and its words are a subsequence of the old text's words. Only a grown or reworded key owes the ledger, and an added key still owes the neighbour matrix and the dogfood table. `check_request_budget.py` still reports a trimmed key as moved, because the lock has to be refreshed by `--update`; it only stops telling the author that the ledger is owed for it. The first lock written in this shape is its own Ratchet commit and raises nothing, and a base lock that still holds bare hashes compares by hash and cannot show a cut, so the first trim after the format change owes the ledger as before. The fixtures are `identity.md` before and after the autofixer's trim in 2b77affff, whose hashes are the lock's values either side of that commit.

The lock keeps the text where the plan sketched a byte count beside the hash, because a hash and a byte count cannot say whether new text is made of the old text's words, and every tool description is one long line, so a line-level subset check would never fire. docs/YI_DESIGN.md section 7.1 and the guardrails table in section 21 say what the lock holds.

Units in this PR: E-ci-live-weekly and HD-G02-surface-trims.
