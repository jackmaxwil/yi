The console has a browser pane (Closes #1379). ⌘⇧B or ⌥w opens it beside the focused pane, at the last `http://localhost:*` or `http://127.0.0.1:*` URL in that session's transcript, else with its URL bar open; on a browser pane the same chord closes it. A new crate, `yi-browser`, finds the installed Chrome or Chromium (the macOS app bundles, then `google-chrome`, `chromium` and `chrome` on PATH; a new config key `browser.path` overrides) and starts it headless through `yi __fds`, a hidden subcommand that puts the CDP pipe on fds 3 and 4 and execs Chrome. CDP runs as NUL-ended JSON through a router that creates and attaches a page target, sizes its viewport to the pane's pixels at the terminal's cell size, and acknowledges each screencast frame. Headless Chrome sends no frame after a cross-document navigation until the screencast restarts, so the router restarts it on every main-frame navigation. Frames reach kitty as base64 PNG on image ids far above the orb and avatar ids, inside the frame's synchronized update, and a popup over the page lifts the image. Clicks (with double and triple click counting), drags, hover, the wheel, keys and paste reach the page; ⌘, ⌥, ctrl+b and ctrl+c stay the console's, ctrl+l opens the URL bar, and the bar's `‹ › ↻` marks go back, forward and reload. With no Chrome found, or in a terminal without kitty graphics, the pane says so in a `[…]` row that names what it looked for and the fix. With no Chrome installed and no `browser.path`, the pane installs a pinned one on first use: it runs `yi plugin add chrome` in the background, once per console however many panes wait, shows an `[installing chrome-headless-shell 155.0.8059.39 (~100 MB) with …]` row naming the command and the directory while it runs, then launches the headless shell, or shows the add's `error:` line verbatim.
