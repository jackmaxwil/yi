# D169: host-written memory, one markdown file per fact

Status: accepted

## Decision

Host-written memory, one markdown file per fact: `~/.yi/projects/<encoded canonical
repo>/memory/` for the repository (the lane's git-common-dir, so worktrees share it)
and `~/.yi/memory/` for every repository; YAML frontmatter `name`, `description`,
`type` read leniently (a YAML subset with one nesting level, then a JSON object,
then none; a broken block still indexes by its first body line and is counted as
unparsed, never refused on disk); `MEMORY.md` appended, human-editable, reconciled
once at session start and never reordered; `usage.json` counts sessions, saves and
reads; the root session's yard carries one untrusted `memory` block from zero notes
on, its header the save template and the only documentation; `memory.save(markdown,
**fields)`, `memory.read(name_or_hook)`, `memory.forget(name)` over the host bridge,
root session only, three saves per session, refused at the boundary with the field
and the bound, on a yard fence or `<memory` tag, or on a key-shaped secret; the host
renders every saved file canonically; the TUI shows a dim start line, a dim line per
save and forget, and a HUD `Memory · saved N` row

## Why

PR #285's store was sound but the model was never told the verbs existed, the block
was empty until a save and pointed at files the sandbox cannot open, and seven
positional arguments broke on an alias; the case study is the user's Claude Code
memory directory (50 notes: description median 173 characters, body median 1 417
bytes), which `yi memory import` reads as-is; mid-session recall, triggers and
`/memory` wait on the activation this stage measures (plan
`docs/plans/2026-09-10-memory.md`, issue #373)

## Reversible via

Delete `crates/runtime/src/memory/`, its `attach` call in `wire_fetch`, the TUI port
method and footer drain, `crates/cli/src/memory.rs`, and the `PYTHON_SKILLS` row;
notes stay on disk, unread
