# D401: Yi's own stores are swept from one retention table whose rows judge an entry...

Status: accepted

## Decision

Yi's own stores are swept from one retention table whose rows judge an entry by
liveness first and age second, and keep an entry whose liveness cannot be read; the
first row is the checkpoint shadow repos: one whose project has been gone 7 days is
renamed aside and deleted (the shadow dir's mtime is its last capture, since every
`add` rewrites the index through `index.lock`; a leftover renamed dir is deleted by
the next sweep), one whose project cannot be stat'd, whose nearest surviving
ancestor is a mount root (`/Volumes`, `/mnt`, `/media`, `/run/media`) or a user dir
under `/media` or `/run/media`, or whose config value git escaped is kept, and a
live project's repo is never deleted but, once idle an hour (so a prune never races
an active session's capture), `git prune`d with a 30-day expiry, which keeps every
younger capture and every object it names because captures write no ref, git roots
its traversal in recent objects and the shadow index, and each capture now refreshes
its tree's mtime (`write-tree` returns a cached tree untouched); the sweep runs
about hourly per home on a detached thread from session start, stamping
`~/.yi/retention.stamp` only once it ends and holding `~/.yi/retention.flock` while
it runs, so a second session skips a sweep in flight while a process killed mid-
sweep leaves neither a fresh stamp nor a held lock and the next session runs the
leftover pass, and on demand as `yi gc` (a preview of the counts) or `yi gc --fix`;
the venv sweep also takes the pre-0.111.0 unhashed `kernel-venv`

## Why

On 2026-10-07, 11,633 of 11,635 shadow repos under `~/.yi/checkpoints` (2.8 GB by
`du`) belonged to projects that no longer existed, nothing ever deleted one, and the
live repo of the yi tree was 394 MiB of loose objects; the owner chose "Tests +
cleanup", "Background + `yi gc` command" and "Trim snapshots older than 30 days";
`undo` to a capture older than 30 days stops working, which the owner accepted with
the 30-day choice; a review found that an unchanged project's capture kept a months-
old tree mtime and was pruned minutes later, and that a cut-short delete left a repo
no capture could use

## Reversible via

Delete `retention.rs`, its `sweep_home_hourly` call in `build_session`, the `gc` arm
and `run_gc`, `checkpoint::{work_tree, prune}` and the tree refresh in `write_tree`;
drop the `kernel-venv` name from the venv sweep's filter
