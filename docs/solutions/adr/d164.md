# D164: a family shares one address space for objects, files and transcripts, and...

Status: accepted

## Decision

A family shares one address space for objects, files and transcripts, and the
filesystem is the transport: the root session's `family/` directory (the first
non-`sub-` ancestor of a member's session dir, `RuntimeWiring::family_dir`) reaches
every kernel as `RLM_FAMILY_DIR`; `rlm.put(name, obj)` dills an object there with a
JSON sidecar `{name, owner, at, bytes, type, serializer}` (pickle when dill is
absent), `rlm.get(name)` reads it back, `rlm.ls()` lists the sidecars, and the host
serves a sidecar at `family://<name>`; `rlm.fetch("kernel://<agent>/<var>")` from
another member asks the host for the object, the owner's kernel dills the variable
to `family/<agent>.<var>.dill` in an internal cell and the reader undills it, with
`as_text=True` (or a host with no family dir) keeping the 8 KiB repr;
`tree://<agent>/<path>` reads a file from a member's own checkout (the parent's cwd,
or an isolated child's worktree), read-only, lexically confined to that checkout and
walled by the reader's `deny_read`

## Why

Before this the only ways a child's result came home were `context_keys` at spawn (8
variables of 4 KiB, one way), a `repr` cut at 8 KiB, and `merge_worktree`, so a
DataFrame or a corpus shard had to cross the transcript as text and a parent could
not inspect a worktree child's file before merging (issue #298;
docs/plans/2026-09-08-pass-levers.md S8); both kernels share a disk, so a file is
the cheapest whole-object channel and needs no bytes on the comm

## Reversible via

Delete `put/get/ls`, `dump_variable`, the two schemes and `MemberTrees`;
`context_keys` and the text repr remain
