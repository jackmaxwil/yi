# D339: a tool judges the file it opened, not the name a check saw (amends D323)

Status: accepted

## Decision

A tool judges the file it opened, not the name a check saw (amends D323): every file
a tool call names (read, a directory's skeleton heads, a glob, write, edit with its
`MV` destination and its deletes, grep and grep `apply`, `get_context`, and
`fetch::read_text` for every scheme that serves a host file) opens through
`ReadGate::open`, `open_write` to write or `remove` to delete; it resolves the path,
judges the resolved path with D323's gate, D15's destroy gate for a write and the
wall lists the caller passes (`deny_read`, and `deny_write` too for a write), then
opens that resolved path with no link left to follow: `O_NOFOLLOW_ANY` on macOS, and
on Linux the kernel's name for the descriptor (`/proc/self/fd/N`) must equal the
path judged. A write opens an existing file untruncated or creates a missing one
with `O_EXCL`, and truncates through the handle; a delete checks, just before the
unlink, that the name still has the identity of the file it opened, the one window
left, since std has no `unlinkat`. The document converter reads the judged bytes on
stdin, never the name. The broker still judges the name first; a refusal at the open
is a `PermissionDenied` error naming the resolved path. Commands contained by
Seatbelt were never exposed, since the kernel resolves links when it applies the
profile

## Why

The reviews of #885, #903 and #911 read a key 40 times in 20,000 tries by swapping a
link between the check and the open, and a write, an edit and a grep `apply`
reopened the name after its check the same way. `O_NOFOLLOW` guards only the last
component and std has no `openat`, so opening the resolved path with no link
anywhere on it is the std-only way to make the path judged the path opened; reading
the descriptor's path on macOS (`F_GETPATH`) or `openat2` on Linux needs `unsafe` or
a new direct dependency

## Reversible via

Open the name in `ReadGate::opened` without `no_link` and `opened_at`
