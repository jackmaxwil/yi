# D339: the model may ask to accept a todo, and the user, or the classifier in auto...

Status: accepted

## Decision

The model may ask to accept a todo, and the user, or the classifier in auto mode,
answers (amends D193): `accepted_by_user` (alias `accept`) joins the plan tool's
model ops; the root tool, wired with the session's permission broker and store
(`authority::Confirming`), sends it through `authority::submit`, so the owner's
request is confirmed exactly as the CLI's and the console's are; the description
shown names the todo and the model's `note`; `PermissionBroker::confirm_judged` lets
the approver answer first when the mode is auto and an approver is set, judging the
acceptance at the stricter threshold for a call it cannot prove (0.98 by default),
and only for `accepted_by_user` (fuse reset, repair and resolve still need a
person); an allow mints `Actor::Classifier`, writes no user message, records
`classifier` as the journal actor and lands `Done { AcceptedByClassifier }`, which
the reducer replays from the record and a worktree todo takes like the user's;
anything else asks the person; `can_confirm` admits a session with the approver and
no prompt; with no broker wired the refusal is `NoConfirmer`; a checker timeout's
refusal names the call

## Why

Session 01a0f41f: a contract item the verifier could not run abstained, and with no
route to the existing `accept` (the CLI passes no confirmer, the tool never reached
`authority::submit`) the model weighed "gaming" the contract; the owner: "Yi should
have an escape hatch for skipping plan gate run check", chose "Model asks, you
approve", and "The approval should be auto handled by classifier, if classifier is
enabled". `Resolution` has no `Other`, so a binary from before this row refuses a
plan file carrying `accepted_by_classifier`

## Reversible via

Drop `Actor::Classifier`, `Resolution::AcceptedByClassifier`, `confirm_judged`,
`can_confirm`, `authority::accept` and `Confirming`, move `Accept` back past
`MODEL_OPS`
