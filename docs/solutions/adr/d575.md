# D575: every finished reply's `timestamp` is the wall-clock millisecond it ended,...

Status: accepted

## Decision

Every finished reply's `timestamp` is the wall-clock millisecond it ended, read
through `StreamFn::now_ms` (the runtime's `ProviderStream` answers
`yi_session::now_ms`, a stream with no clock leaves the reply's own) and written by
the loop before the reply joins the history or is stored, so reclaim's cache-read
test (D558) and lapse test (D387) read real replies, and on any route, priced ones
included, a session whose newest reply is older than its cache TTL (a resumed one,
or one left idle) now cuts every aged result as `expired` on its first request,
D387's lapse branch, which never ran before; a reply stored before this carries 0
and is still no evidence of either, so an old session ages nothing until its first
new reply

## Why

No Yi writer stamped a reply: 0 of 32,908 assistant messages in the owner's sessions
carried a time, while Pi's writer stamps every one (when it creates the output,
before the request; Yi stamps the end, as its cache record does, so the lapse test
errs late and never cuts a warm cache), so reclaim's reply filter dropped them all;
on a $0-priced route that reads its cache (the Kimi lane, 25 of 34 replies with
cache reads) every aged result was cut at once, two back-to-back cache rewrites in
the audit's 20-request harness instead of one, and the lapse branch never ran;
stamping changes only the field's value, never the shape or field order, and reading
a 0 as "long ago" would cut every old session's results as expired on its first
resumed request

## Reversible via

Delete the stamp line in `yi_loop::run::stream_assistant_response` (or return `None`
from `ProviderStream::now_ms`); replies go back to 0 and reclaim to the price test
alone
