# D328: every contained spawn has loopback and no other network, and kernel...

Status: accepted

## Decision

Every contained spawn has loopback and no other network, and kernel connection files
are hidden from every sandbox but their own kernel's (amends D87, D241, D323 and
D324): `Sandbox::policy` ends every profile with `network-bind` and `network-
inbound` on `(local ip "localhost:*")` and `network-outbound` on `(remote ip
"localhost:*")`, so the bash tool, a kernel and its `bash()` jobs bind and connect
on 127.0.0.1 and `::1`; the document converter, which parses untrusted files, keeps
no network (`Sandbox::wrap_offline`); every contained start sets `JAVA_TOOL_OPTIONS`
(appended to the inherited value) to `-Djava.net.preferIPv4Stack=true`, since a
JVM's dual-stack socket dials 127.0.0.1 as `::ffff:127.0.0.1`, which Seatbelt
refuses, and Gradle, Maven, sbt and Kotlin lost loopback; `Sandbox::loopback`,
`kernel_policy` and `KernelService::set_sandbox` are gone; unix sockets, other hosts
(IPv4, IPv6, `::ffff:`-mapped) and name lookups stay refused, the last because the
base policy grants no resolver, and `sandbox_refusal` reads a resolver failure
(`resolve host`, `nodename nor servname`) as the sandbox's; connection files move
from `$TMPDIR/yi-kernel-*` to `~/.yi/kernel-connections/<pid>-<n>`, a credential
store, so every profile and the read gate refuse them, and only the kernel's own
prefix (`kernel_prefix(connection_dir)`) re-allows its directory, placed last so it
outranks the deny and bound as its parent resolved plus its own name, never as the
directory resolved on disk, where the kernel writes and could plant a link; the host
makes that directory afresh at each start, creates the file with `create_new`, and
removes the directories of dead pids a crashed yi left. What loopback exposes,
probed on macOS 26: Seatbelt's `localhost` is every address of this host and the
wildcard, and no rule names anything narrower (`host must be * or localhost`; a
remote-peer deny on inbound does not fire), so a contained process can listen on
0.0.0.0 and a LAN or tailnet peer can connect in (a second host did), and it reaches
any service this host serves on any of its addresses; every TCP or UDP service on
127.0.0.1 is reachable: a database or dev server with no auth, Docker's TCP API or
Chrome's DevTools port when enabled, `yi login`'s OAuth callback while it waits
(PKCE and `state` guard it), a local DNS forwarder or HTTP proxy, which would carry
traffic past loopback, and any service whose token sits in a file reads leave open,
such as a Jupyter server or kernel whose connection file is in
`~/Library/Jupyter/runtime`, or a kernel an older yi still running keeps in
`$TMPDIR`; the kernel profile has allowed the listening half since D241; yi's daemon
socket, docker.sock and the ssh-agent and tmux sockets are unix sockets and stay
refused; a dual-stack client that dials `::ffff:127.0.0.1` is refused, which the JVM
option covers for Java

## Why

The owner: "a kernel cell should be able to open outbound connections to localhost",
and stage 2b's contained `cargo test` must bind 127.0.0.1 (#599); with outbound
loopback open, a connection file in `$TMPDIR` let any sandbox read another kernel's
key and rewrite its file (a second kernel did both), and the key runs code in that
kernel; a port deny under `localhost:*` never fires (#592 round 5), so no local
service can be carved out

## Reversible via

Drop `NETWORK_POLICY` from `Sandbox::policy_for`, restore `Sandbox::loopback`, and
`make_connection` under `std::env::temp_dir()`
