# D316: every stream a producer cuts for the model spills whole under the recovery...

Status: accepted

## Decision

Every stream a producer cuts for the model spills whole under the recovery dir
(`~/.yi/tool-output`, `ToolContext::recovery_dir`), and the cut names the file as
`[full output: path]`, which `read` opens: `reduce::Spill` holds the first 64 KiB in
memory and the rest in a `.part` file beside it, stops writing at 256 MiB, is
renamed `<xxh32>.txt` when kept (the tee's naming, so equal outputs share one file)
and removes its `.part` file when dropped unkept; bash's `drain_capped` writes both
streams of a call into one spill as the chunks arrive, kept when a stream passed its
30,000-byte cap or the two passed the reducer's 8,192-byte floor; the reducer no
longer tees and points a lossy reduction at that spill; a background job's report
names it; the ipython bridge (`KernelBridge::execute_cell` gains `recovery_dir`)
feeds a cell's stdout and stderr to a spill (`CellSpill`) through yi-kernel's
uncapped `on_stream` and adds the pointer to the cell's notes when either passed
65,536 characters; the file is written by yi's own process under its own HOME, never
by the sandboxed command, never in the working tree or /tmp, and a missing HOME
keeps nothing and says `[output truncated]` as before

## Why

A cut stream's middle existed nowhere, and the reducer's `[full output: P]` held the
cut text, not the output (dogfood 2026-09-27, plan T3); weighed: kept files are
never swept, as the tee's were not, so `~/.yi/tool-output` grows until a TTL sweep
lands; a stream past 256 MiB keeps its first 256 MiB; a displayed value
(`execute_result`) past the kernel's cut has no stream hook and stays cut with no
file; the user's own cells (`execute_user_cell`) pass no recovery dir

## Reversible via

`run_captured_live` with `spill_dir: None` and the reducer's `tee` restored; the
ipython bridge without `on_stream`
