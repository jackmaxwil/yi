# D52: completion claims are host-verified

Status: accepted

## Decision

`goal.update(complete)` runs the goal's executable `check` before accepting the
claim: exit 0 passes, anything else rejects. A plan task's done claim runs the
task's own `check` and validates the reported evidence against the task's
`schema`. A rejection is persisted, not just returned — the goal keeps the
failing output tail in `checkFailure` and carries it into the continuation
prompt, and the task moves to `Blocked` with the evidence as its reason. A
blocked report never runs the check; only a completion claim does.

## Rationale

Factory's 2026-08 result is the anchor: a single agent scored a median 56.7
against 89.3 for the same work measured by an independent completion standard.
Checks written during implementation inherit implementation's scope, and a
self-administered audit stops as soon as it is satisfied. §16's TRACE rule —
enforced beats recalled — applied to the last step of a task rather than to its
first.

This revises G2, which let the model report terminal state. The report still
stands; the host is what decides whether it is true. The model cannot mutate the
check through `update`, so the standard is fixed for the run.

## Reversal path

Drop the check run in `GoalService::update` and `PlanService::verify_done`. The
`check`, `checkTimeoutMs` and `checkFailure` fields are additive `Option`s and
stored goals keep parsing without them.
