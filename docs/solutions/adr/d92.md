# D92: the gate's lanes run in parallel, and its suite runs under nextest

Status: accepted

## Decision

Three changes to how the same gate is scheduled, none to what it checks.

`just lane <name>` runs one lane of `just check` and carries prepush's own
invariant — that the gate regenerated nothing. `just prepush` becomes
`(lane "check")`. `.github/workflows/pr.yml` runs a `{os} x {lint, guardrails,
test}` matrix of `just lane`, so the gate pays its longest lane rather than
their sum.

`just test` prefers `cargo nextest run --workspace` when `cargo-nextest` is on
PATH and falls back to `cargo test --workspace` when it is not. Because nextest
does not run doctests, `cargo test --workspace --doc` runs beside it rather than
letting them quietly leave the gate.

`.config/nextest.toml` gains a `subprocess` test-group capped at three
concurrent, covering the twelve test binaries that spawn `yi` as a child.

`[profile.dev]` takes `debug = "line-tables-only"`, and `[profile.dev.package."*"]`
takes `debug = false`.

## Rationale

Profiled, not guessed. Of the 6m06s that survived D91 on a macOS runner:

| phase | wall |
|---|---|
| fmt-check + clippy | 57s |
| guardrails (37s of it `check_request_budget.py`, which shells out to `cargo test`) | 58s |
| test-profile compile + link | 74s |
| test run, 671 tests in 101 binaries | 177s |

Two of those numbers are scheduling rather than work.

`cargo test --workspace` runs the 101 binaries **serially**. Five of them —
`cli_surfaces` at 74s, `mcp_oauth` at 36s, and `tui_drive`, `acp_protocol` and
`recursion_e2e` at about 16s each — are 96 % of the run, while the remaining 95
finish in twelve seconds between them. nextest pools every test from every
binary instead.

And `lint`, `guardrails` and `test` never depended on one another, so one job
running them back to back paid their sum for no reason a dependency could name.

**The test-group is the half that had to be measured before it could be
written.** Turned loose in one global pool, nextest times out 14 tests and takes
121.9s: every test in the twelve binaries that drive `yi` spawns a child that is
itself multithreaded, and they oversubscribe the machine against 600
microsecond-scale unit tests. Bounded, the same 671 tests run green in 57.0s —
faster than the unbounded run that failed, and faster than `-j 3` across the
whole run at 66.4s. The cap bounds scheduling, never coverage: every test still
runs, and a test-group is the mechanism `.config/nextest.toml` already existed to
express, for the same reason, for the kernel tests.

The invariant moves onto the lane rather than staying on the whole gate because
a split run would otherwise stop asserting it, silently — the failure mode
pre-push exists to prevent. The cargo fallback is there so a fresh clone with
nothing installed still runs the suite.

The debuginfo trim is the one change that touches build output rather than
scheduling. Generating debuginfo and linking it into 101 test binaries was a
fifth of the wall clock; a backtrace through serde's frames is not what anyone
reads, and `file:line` on Yi's own frames survives `line-tables-only`. A smaller
`target/` is also a smaller cache, which compounds with D91's.

The case for the timeout is not hypothetical. A Linux job on the D91 branch sat
in `just prepush` for 29m29s and had to be cancelled by hand, against 6m48s for
the same commit on the previous attempt. `cargo test` has no per-test timeout and
would have held that runner to the six-hour job ceiling; the `terminate-after = 2`
over a 30s period that `.config/nextest.toml` already carried kills it in sixty
seconds.

`.github/` stays what D84 requires: it names which lane runs on which runner and
nothing else. Every rule it invokes is a justfile recipe the git hooks also run.

## Reversal path

Collapse the matrix back to one `just prepush` job, drop `lane` and `lint` from
the justfile, revert `test` to `cargo test --workspace`, and delete the
`subprocess` group and its override. The profile stanza reverts independently.
