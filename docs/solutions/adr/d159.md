# D159: an OpenRouter request routes by throughput, a mid-stream error keeps its...

Status: accepted

## Decision

An OpenRouter request routes by throughput, a mid-stream error keeps its message,
and a dropped stream that showed nothing runs once more: every request to an
`openrouter.ai` base URL carries `provider: {"preferred_min_throughput": {"p50":
20}, "preferred_max_latency": {"p50": 10}}` (0.190.0; the first `{"sort":
"throughput"}` bought upstreams at about twice the catalog price) unless `routing`
in `~/.yi/config.json` names OpenRouter's provider object verbatim (`{}` restores
its load balancing; never `:nitro`, which prices a priority tier); the chunk mapper
reads the top-level `error` object and `provider` field into `errorMessage` as
`<message> (upstream <name>, code <n>, <error_type>)` and keeps that over the bare
`Provider finish_reason: error`; and the loop, on an error stop whose message holds
no text and no tool call and whose usage or error class says a stream was open
(tokens generated, or a transport class such as `Error while decoding chunks`, now
`transport:closed`), sends one hidden `custom{stream_retry}` carrying the error and
runs the turn again, once per prompt, counted by `extract.py` as `stream_retry`

## Why

Two photonic attempts on the 2026-09-08 rerun ended with `finish_reason: error`
after about 900 s of a single turn at five to ten tokens a second, cost 0, on an
upstream named Wafer, while the previous day's turns ran on Novita at forty tokens a
second; OpenRouter's default routing weights by inverse-square price and fails over
only before tokens reach the client, the docs' own lever is `sort: throughput`
(deterministic, no price change), and Yi had dropped the chunk's error object and
ended the run on a stop that delivered nothing (docs/plans/2026-09-08-failure-
paths.md follow-up, OpenRouter provider-routing and errors docs)

## Reversible via

Drop `routing_params` and the config field; `error_chunk_text` and `stream_retry`
each delete cleanly
