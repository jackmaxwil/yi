# D141: the console owns text selection because it owns the mouse

Status: accepted

## Decision

The console owns text selection because it owns the mouse: with `EnableMouseCapture`
on, a drag over any pane is read off the drawn frame —
`crates/console/src/select.rs` paints the cells the drag covers and returns their
text, in reading order with the rows between the ends taken whole — and the release
hands that text to the terminal's own clipboard over OSC 52, through the `osc_out`
channel the notifications already use; an editor pane keeps its own text selection
(the cursor and the keys need it) and copies the same way on release, a click that
never moved leaves no highlight, and any key clears one

## Why

The console has captured the mouse for pane focus, split drags and scroll since its
first version, which silently takes away the one copy path every terminal has, and nothing
replaced it: text on screen could not be copied at all, and the editor's own mouse
selection highlighted a run it never put anywhere. Reading the drawn buffer rather
than each pane's model means one implementation serves chat, notebook, diff, sidebar
and editor gutter alike and copies exactly what is on screen. OSC 52 is the
terminal's own clipboard: it works over ssh, adds no dependency where a clipboard
crate would, and `pbcopy` is a process spawn the guardrails disallow outside `yi-
tools`. Telling the user to hold shift for the terminal's bypass was the zero-code
alternative and is not one: it is per-terminal, absent in Terminal.app, and copies
the frame's columns across pane borders

## Reversible via

Drop `select.rs`, the drag arms in `app/mouse.rs` and the paint in `draw`; the mouse
focuses panes and drags splits exactly as before, and the editor's `release` returns
to clearing an empty selection
