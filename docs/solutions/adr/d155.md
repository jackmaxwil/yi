# D155: a todo item has an id and a label matches by unique prefix

Status: accepted

## Decision

A todo item has an id and a label matches by unique prefix: every item carries
`t<n>`, minted per session and never reused, rendered in every listing and `next:`
line, accepted by every op beside `label`; a label resolves exact, then by id, then
as an id followed by that item's own label (`t1 <label>`), then by a unique case-
insensitive prefix of eight characters or more with backticks stripped, and an
ambiguous prefix is refused naming the candidates; a label over eighty characters is
cut into its note, never refused, and a cut label shows `…`; a call with no `op`
whose fields name one op (`list` is set, `items` is append, `label` with `evidence`
is done, with `reason` is drop, with `on` is block) takes it and says so, as does an
`init` carrying only `list` (read as set) or a `set` carrying only `items` (read as
init); `todos` reads as `items`, and an item sent as a `{"label": ...}` object reads
as its label; every argument error ends with a full call for its op that names the
item by id, and `op is required` shows the done call

## Why

Row 0021 spent four to six turns per attempt on `no todo labelled`, `exceeds 80
chars` and `op is required`, and the D148 seeding cut bun's decisive clause mid-word
at eighty characters so all three attempts steered by the truncated label (issue
#279); in the 2026-09-11 v4 sweep 41 of 352 todo calls errored, 15 of them on those
shapes, and all 8 `no todo` errors named a label while 116 id references resolved

## Reversible via

Drop the `id` field (additive, old sessions rehydrate without it), the prefix and
id-and-label steps, the inference and the shape readings
