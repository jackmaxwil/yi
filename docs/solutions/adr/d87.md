# D87: the IPython kernel starts inside the session Seatbelt

Status: accepted

## Decision

The kernel process is spawned as `/usr/bin/sandbox-exec … -- <python> -m ipykernel_launcher`.
The profile is the session's write and credential-read set, plus loopback TCP for Jupyter's
ZMQ, plus `~/.yi` so ipykernel can write bytecode in its venv. Bash wrap is unchanged: no
network rule at all.

yi-kernel takes that wrap as a `(program, args ending --)` prefix. It does not depend on
yi-tools.

A later profile change disposes the running kernel; the next cell starts under the new wrap.
Where Seatbelt is missing, `workspace_sandbox` is `None` and the kernel stays unsandboxed;
containment still degrades to ask.

## Rationale

P1 left the kernel out because it is long-lived and any later cell may touch a new root. That
is a restart, not a reason to skip the OS sandbox. A Python `sitecustomize` is the arms race
Praxist already lost (`%%bash`, `subprocess`, `ctypes`, an alias captured before import).

## Reversal path

Drop `KernelOptions.wrap` and `KernelServiceOptions.sandbox`. Bash wrap does not move.
