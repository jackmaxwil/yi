# D70: binary_size is local-only too, because its baseline names a target

Status: accepted (supersedes the `binary_size` half of D68)

## Decision

`check_binary_size.py` is skipped when `CI` is set, on the same terms as
`startup`, and the dist build step D68 added to `ci.yml` is removed with it.
Both gates that read `target/dist/yi` now run only where the budget was
measured. Locally nothing changes.

## Rationale

D68 kept `binary_size` in CI on the grounds that it is deterministic: it reads
a file's length against a budget stated in bytes, and the answer does not
depend on what else the machine was doing. That is true, and it is not
sufficient. The budget is deterministic *for a target*, and §13.3 names the
target in the row itself — "dist binary, macOS arm64, default features". CI is
`ubuntu-latest`.

The measurement settled it on the first run. The same tree that produces
4,636,976 bytes on macOS arm64 produces 6,980,216 on the Linux runner, so the
gate compared a Linux binary against a macOS baseline and failed by 2.3 MiB
while nothing was wrong. A byte-exact ratchet cannot cross an ABI.

Giving CI its own Linux baseline was the alternative and is rejected: it is a
second budget to ratchet, drifting on its own schedule, guarding a binary
nobody ships, and §13.3 states one platform on purpose. The dist build goes
with the gate — an LTO build per run bought nothing once the only gate reading
its output stopped running there.

What survives from D68 is its shape: CI runs every gate that is meaningful
where CI runs, the two that are not are skipped with a printed line naming the
row rather than dropped in silence, and both still run on the machine where
the budget was set.

## Reversible via

Delete the `CI` guards in `check_guardrails.sh`; restore the dist build step in
`ci.yml` if `binary_size` is ever given a per-target baseline.
