# D192: plan ops are a host request, lifecycle notices wake, and wait is cursored

Status: accepted

## Decision

Plan ops are a host request, lifecycle notices wake, and wait is cursored: `plan.op`
is registered beside `plan.get` on every kernel's registry with payload
`{request_id, plan?, expected_revision?, op, args}`, runs the same `parse_op` and
`PlanEngine::apply` the JSON plan tool runs, fixes the actor at registration
(`Owner` on the root kernel's registry, `Child(name)` on a child's) and refuses an
`actor` key; `expected_revision` is compared on the plan the op names for every op
but `view` and `init`, a duplicate `request_id` within one process returns the
cached reply, and the reply is `{ok, request_id, revision, text}` or `{ok: false,
request_id, revision, refusal: {code, message}}`; a child's terminal notice reaches
its parent through `wake_idle_hook`, so an idle parent starts a turn on it and a
running one reads it at its next turn; `rlm.wait(timeout, cursor)` returns `{cursor,
changed, states, notes}` from the family epoch, drains nothing shared, wakes on a
delete, and keeps `updated` as an alias of `changed` for one release; the kernel-
side `python/skills/plan/` is deleted (extends D137 and D165)

## Why

The kernel-side plan skill called four host names nothing registers (`plan.create`,
`plan.update`, `plan.edit`, `plan.split`) and claimed done was host-verified, so a
model that followed it wrote nothing; a child's terminal notice went through
`notice_hook`, which cannot start a turn, so a parent that ended its turn blocked on
a child sat idle until the user spoke; `wait` drained a shared counter, so two
waiters stole each other's updates, a late waiter slept to its deadline, and
`RLMSpawnHandle.result` polled `list_subagents` every 0.5 s instead

## Reversible via

Unregister `plan.op`, restore the `notice_hook` line in `wiring.rs`, restore
`take_pending` in `mailbox.rs` and the poll in `result`; persisted deliveries
survive the revert
