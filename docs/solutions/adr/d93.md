# D93: the startup budget is scored on the minimum, not the mean

Status: accepted

## Decision

`scripts/guardrails/check_startup.py` runs hyperfine with `--warmup 10 --runs
50` against `target/dist/yi` and compares `results[0].min` — the fastest of the
50 runs — to the unchanged cap in `startup_ms_budget.json` (`{"yi --version":
5.0}`). It previously compared the mean. The cap itself does not move.

## Rationale

Startup time is bounded below by real work and only inflated from there by
whatever else the machine is doing; the fastest of fifty runs is the closest
reading of the binary's own cost, while the mean also prices contention on the
box. `just guardrails` depends on `build-dist`, so this gate runs right after
an LTO build more often than not, and the mean read 6.5-7.4 ms there against
3.1-4.4 ms idle on the same binary — enough to block a push in a code path
`yi --version` never touches.

The cap staying at 5 ms against a smaller statistic makes the gate looser than
it was against the mean. That is the deliberate trade: a red reading now
indicts the binary, not the box it happened to run on, so re-running the gate
idle stops being an explanation for a failure. `.ruler/010-done-bar.md` states
this directly — a stale-cache theory should be tested by touching the crate's
`lib.rs` and rerunning, not by hoping for a quieter machine.

## Reversal path

Revert `min` to `mean` in `check_startup.py` and restore the wall-clock
exception in `.ruler/010-done-bar.md`.
