# D170: a catalog model's `headers` reach the wire

Status: accepted

## Decision

A catalog model's `headers` reach the wire: `yi_ai::request::headers_for` merges the
`headers` object of a `~/.yi/catalog/<provider>.json` model entry over the adapter's
own set, matched case-insensitively so an overlay name replaces the adapter's rather
than riding beside it, an empty value removing it outright, and all three adapters (anthropic-messages, openai-completions,
openai-responses) build their headers through it. `get_json` is untouched: catalog
refresh is per-provider and has no model to read.

## Why

`Model::headers` had been in the schema since the bundle's first parse with no reader.
A catalog overlay carrying it changed nothing, so anyone fronting a provider with a
gateway that wants its own auth, tenant or routing header had no route short of editing
an adapter and rebuilding.

The match is case-insensitive because ureq sets every pair it is handed: a
case-sensitive merge would send `Authorization` twice and let the far side pick one,
which is a silent wrong-credential bug rather than a loud one. The overlay wins by name
so the file can retarget auth, not merely decorate it.

An empty value removes the header rather than blanking it: retargeting auth at a
gateway means the adapter's `x-api-key` has to go, and ureq sets every pair it is
handed, so a blank would arrive as a malformed empty key instead of an absent one.

The overlay file already decides `baseUrl` under D128, so it is an equally trusted input
either way — this adds no new trust, only a second field read from a file that already
chooses where the request goes.

## Reversible via

Delete `headers_for` and restore each adapter's literal header vec; `Model::headers`
goes back to an unread field and every request sends what it sent before.
