# D95: the workspace shell is a new crate speaking ACP to the daemon

Status: accepted

## Decision

`yi-console` (`crates/console`, `yi console`) is a new crate: an ACP client
over the `yi serve` daemon's Unix socket that renders locally from the
`session/update` stream it receives. A pane is a session; a workspace is a
repo root. The daemon stays the only session owner — the console adds no new
runtime coupling, and its manifest depends on `yi-types` and `yi-tui` alone
(`crates/console/Cargo.toml`; `scripts/guardrails/boundaries.toml` pins
`"yi-console" = ["yi-types", "yi-tui"]`), no new external dependency beyond
what those crates already carry.

The client protocol is a synchronous state machine driven from the UI loop
with two dumb IO threads around one `UnixStream`
(`crates/console/src/client.rs`): bounded line framing with a 32 MiB frame
cap, a `sync_channel(4096)` for inbound events so a lagging UI backpressures
the socket rather than buffering unbounded, and reconnect with a 250 ms
starting backoff. The reducer (`crates/console/src/app.rs`) holds a
pending-request map keyed by request id with a 10 second deadline
(`REQUEST_DEADLINE`) that all fail on disconnect. Because the state machine is
synchronous and in the UI loop rather than spread across the IO threads, the
existing drive-script harness can run the real reducer against a fixture
daemon on a scratch socket.

## Rationale

`yi-tui` is an inline-viewport, single-session surface under its own crate
size ceiling, and the hardest code in it — `insert_before` commit, reflow, the
vendored terminal — is specific to that one inline viewport. A pane shell
needs the alt screen and retained per-pane buffers instead, so extending
`yi-tui` in place would fork its render model inside one crate. The `yi-orb`
split (D73) is the precedent for pulling a genuinely separate render model
into its own crate rather than growing the ceiling to fit it.

Rendering client-side, from semantic `session/update` events, avoids the
server-frame-streaming shape a terminal multiplexer like herdr uses — protocol
versioning for cell grids, blit encoders, foreground-client size arbitration.
Yi's panes are semantic event streams, not terminal cells, so the daemon never
needs to know how a pane is laid out or sized; the console reconstructs the
view from the same update stream every ACP client already receives.

## Reversal path

Delete `crates/console`, the `console` arm in `yi-cli`, the `_yi/seen` request
arm and the unseen-ledger fields in `crates/acp/src/daemon.rs`. `session/list`
keeps ignoring its `cwd` parameter, and the drive helpers stay in `yi-tui` as
unused public functions.
