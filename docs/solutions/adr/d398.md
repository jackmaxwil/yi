# D398: reclaim keeps the newest `read` of a file out of every cut only when the...

Status: accepted

## Decision

Reclaim keeps the newest `read` of a file out of every cut only when the session has
edited that file; both sides come from the `[path#TAG]` headers the tools print (a
read's, a glob read's per file, an edit's including a move's destination, a
write's), matched by path suffix since the view has no cwd; the newest read of a
file only read is cut like any aged result, and the annotate tool's discard refusal
reads the same rule (amends the reclaim decision of #1149)

## Why

Every file read once is its own newest read, so no `read` result was ever cut:
dogfooding `yi ask` on glm-5.3-flash, eight 12 KB docs read once each stayed in the
prompt for all 17 requests while the same task through `cat` was cut from about 36k
to 17k tokens; an edit needs the tags of its file's newest read, a file never edited
does not, and the cut's placeholder already names the read that restores it

## Reversible via

Protect every newest read again in `reclaim::newest_reads`
