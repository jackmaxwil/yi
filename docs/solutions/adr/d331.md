# D331: every call the gate allows runs contained where a sandbox exists, outside...

Status: accepted

## Decision

Every call the gate allows runs contained where a sandbox exists, outside yolo (#600
stage 2b; amends D312 and D324): a `Decision::Allow` for bash (a proof such as `git
status`, `cargo test` or `cargo build`, a session rule or grant, a config `allow`)
becomes `Containment::Contained` in `PermissionBroker::decide_call`, with the kept
write grants as `widen` and the wall's `deny_write`/`deny_read` in the profile, so
walls, credential stores and the tree's bounds are enforced by the OS for every such
call, not by spelling at the tool seam; an allowed command that `leaves_sandbox`
(`needs_host`: a network program, a git network verb, an install; or a credential
read) runs outside and its result carries a `sandbox:` line saying so, as does an
approval that escalated; after a contained run of an allowed command was refused,
the next such call asks as a refused contained one does, except that a kept session
rule on a refusal naming no path runs it outside with no question (the owner:
"Always = session pass (Recommended)"); `--yolo`, a platform with no sandbox and a
container child's commands stay as they were; an `exec://` source, which only runs
on the host, is still admitted when the gate allows it outright
(`Containment::Contained { gate_allowed: true }`); `yi gate explain`'s `sandboxed`
is true for such an allow

## Why

#889 and the dogfood re-run of 2026-09-28: an allowed bash call ran with no sandbox,
so a proven-safe `sort -o` wrote outside the tree, `cat` read a walled file by a
relative spelling or a credential store through a link in the tree, and `curl`
reached the network while the tool text said "no network"; #599 (D329) gave
contained spawns loopback, so a contained `cargo test` that binds 127.0.0.1 passes

## Reversible via

Map `Decision::Allow` back to `Containment::Uncontained` in
`PermissionBroker::allowed_outcome` and drop the `sandbox:` line from `ToolAdapter`
