# D331: every bash call the gate allows runs contained where a sandbox exists,...

Status: accepted

## Decision

Every bash call the gate allows runs contained where a sandbox exists, outside yolo;
an `exec://` source still runs on the host (#600 stage 2b; amends D312 and D324): a
bash `Decision::Allow` (a proof such as `git status`, `cargo test` or `cargo build`,
a session rule or grant, a config `allow`) becomes `Containment::Contained` in
`PermissionBroker::decide_call`, with the kept write grants as `widen` and the
wall's `deny_write`/`deny_read` in the profile, so walls, credential stores and the
tree's bounds are enforced by the OS for such calls, not by spelling at the tool
seam; `leaves_sandbox` judges each segment (`yi_permission::host_need`: a network
program, a git network verb, an install verb, labelled `installs`; or a credential
read), and an allowed command runs outside only when it parses strictly and every
segment must leave, with a `sandbox:` line in its result, while a compound mixing a
leaving part with one that could stay inside, or a command the strict parser gives
up on (a newline, `$(…)`, backticks, `<(…)`, an unspaced `&`, and now `$` or a
backtick inside double quotes), asks; `git remote update` and `git remote prune` ask
as `git fetch` does, since `-c remote.<x>.uploadpack` makes them run a command on
the host; an approval that escalated says so in its result too, and a `job=N` wait
or kill gets no line; after a contained run of an allowed command was refused, the
next such call asks as a refused contained one does; "always" on a refusal naming no
path keeps that exact command (its exact bytes plus the directory) as a session
rule, offered as "this exact command, outside the sandbox, for the rest of this
session", and only that exact rule passes it outside later, never a scope grant (the
owner: "Always = session pass (Recommended)"); with no one to ask (a headless run
below `--yolo`) such a retry is denied with what works: `--yolo`, or keeping writes
inside the tree (`CARGO_TARGET_DIR` under the worktree), and such a compound with
"split it into separate calls, or rerun with --yolo"; a configured `allow` does not
widen it unasked, since the rule names a command, not the directory one run reached;
`--yolo`, a platform with no sandbox and a container child's commands stay as they
were; an `exec://` source (heartbeats, plan and todo waits), which only runs on the
host, is still admitted when the gate allows it outright (`Containment::Contained {
gate_allowed: true }`) and runs uncontained, as before; `yi gate explain`'s
`sandboxed` is true for an allow that stays inside

## Why

#889 and the dogfood re-run of 2026-09-28: an allowed bash call ran with no sandbox,
so a proven-safe `sort -o` wrote outside the tree, `cat` read a walled file by a
relative spelling or a credential store through a link in the tree, and `curl`
reached the network while the tool text said "no network"; #599 (D329) gave
contained spawns loopback, so a contained `cargo test` that binds 127.0.0.1 passes;
the review of #933 found one leaving segment carried a whole compound out (through
the lenient split too, and a proven `git -c … remote update` ran host code), a
scope-wide pass behind a question that said "this one call", and a headless denial
recommending an allow rule the call already had

## Reversible via

Map `Decision::Allow` back to `Containment::Uncontained` in
`PermissionBroker::allowed_outcome` and drop the `sandbox:` line from `ToolAdapter`
