# D194: completion is verified by the kernel on every path against a frozen attempt

Status: accepted

## Decision

Completion is verified by the kernel on every path against a frozen attempt: a todo
may carry a `contract` (`crates/types/src/plan/contract.rs`, an item list of `cmd`,
`schema`, `example` deciders with a class floor, weights, a threshold and a coverage
floor; `judge` items are refused at declaration until F3a), `start` freezes the
contract and its criteria by digest and refuses a criterion the store cannot serve,
and `done` on every surface (the JSON tool, `plan.op`, the CLI, `set`, `import`,
`repair`, `supersede`) runs plan section 6.3 in order: commit
`verification_requested { token, effect_id, claim }` under the lease, release it,
run the verifier (`plan/verify.rs`: `/bin/sh -c` by absolute path with `env_clear()`
plus the manifest's declared names, its own process group, capped output, one whole-
verification deadline that also reads the session deadline of D177, every protected
path digested before and after the run), re-acquire, compare the whole token
(attempt, version, contract and criteria digests, output digest, snapshot; the
checker ran in a materialization of the step 1 tree under the temp dir, never the
live checkout, so the workspace is captured afresh and a concurrent edit reads as
stale) and commit either the verdict and `Done { VerifiedDone }` as one record or
`done_refused { verdict }`; a moved token commits `verification_stale` and charges
nothing, an abstention charges nothing, and the third refused verdict on one attempt
steps the todo `Blocked { on: User }` as its own recorded transition; a verdict
settles the effect its record names, never the oldest open one for the label;
concurrent `done` calls for one token join the flight registered under the lease,
another process's live claim is refused until it dies or overruns, and a settled
`fail` or `escalate` verdict is replayed rather than charged again while a settled
abstention runs the checks again on the next `done`; the `plan.op` parser refuses
unknown argument keys so a misspelled `contract` or `output` cannot land a todo on
the unverified path; `set`, `reconcile` and `accept` pass the one validator `done`
uses, which refuses every completion of a worktree todo until F0d and refuses `Done`
without a resolution on a contracted or stated-accept todo, so `set` never authors a
resolution; a todo with neither completes on the caller's word as `Done {
resolution: None }` and reports as unverified, the carve-out F3a's judge tier is
for; an imported stated success lands `LegacyUnverified`, a user's acceptance lands
`AcceptedByUser`; the fuzz lane drives contracted todos and asserts no
`VerifiedDone` without a committed `pass` verdict (retires D77's ladder fields;
carries D77's deterministic-protocol intent; stage F0c of `docs/plans/2026-09-12-yi-
operating-system.md`)

## Why

D77's ladder wrote `Done` on the owner's word and its fields were read by nothing,
so a model completed what its own check refused and no record said which product had
been examined; the plan's review found the bypasses gap 1 of the plan's section 1
names: `do_set` built `TodoState::Done { output: None }` itself at
`ops.rs:1007-1041` (R1), a critical abstention could aggregate to a pass (R4), an
old attempt's verdict could land on a restarted todo (R5), and `do_done` validated a
product only where both it and a document resolved, at `ops.rs:836-838`, so an
unserved product passed (R11); the F0c review round found the fuzz invariant vacuous
with no contract ever generated, the parser dropping misspelled keys silently, two
processes running one checker twice and charging two refusals, a verdict settling
the wrong pending effect, `protected` parsed and never read, the journal fixture
pinning a wire shape the code never emits, the verifier ignoring the session
deadline, the refusal cap counting refused transitions as verdicts, and the stale
test never reaching the attempt comparison; the third round found an abstention
replayed forever for an unchanged token, the step 5 snapshot compared against
itself, and the worktree refusal living in `done` alone while `set` completed the
same todo

## Reversible via

Revert to 0.247.0's `do_done`, which completes a todo on `accept` alone; the
`contract` field on a todo reads back as `accept` through the import path for one
release, and a verified record is never downgraded to the unchecked path while
claiming equivalence

the model reads about the contract, with its check and what came back.

## Neighbour matrix

The contract key against the tools the model already has.

| neighbour | overlap | how they differ |
|---|---|---|
| `read` | both name bytes the model wants checked | a criterion is an artifact in the plan store addressed by digest, not a path; `read` cannot address it, and the verifier never opens a path the model names at `done` time |
| `grep` | both search a tree | the checker runs against a materialization of the step 1 tree under the temp dir, not the live checkout `grep` walks |
| `edit`, `write` | both touch the workspace the contract is about | an edit landing during a check cannot make it a pass: step 5 captures the workspace afresh and a moved token commits `verification_stale` (`plan_ops::a_workspace_edited_during_the_check_is_stale`) |
| `bash` | both run a shell command | the checker is `/bin/sh -c` by absolute path with `env_clear()` plus the manifest's declared names, its own process group and one whole-verification deadline; the bash tool's cwd, exports and session are invisible to it, so a contract cannot be satisfied by a shell the model warmed up |
| the kernel | both run the venv | the `schema` and `example` deciders go through the same `run_check_in` a goal check uses; a runner the host cannot spawn abstains rather than failing the product (`plan_verify::an_examples_runner_that_cannot_spawn_abstains`) |

## Dogfood

Run by hand against `target/dist/yi` in a throwaway HOME and an empty git repo: 12 `yi plan`
calls over one plan (init, 6 append, 3 start, 4 done), plus a read of the resulting
`ops.jsonl`. No phase-2 sampler exists yet, so these are the calls, not a corpus.

- The red-then-green `cmd` contract is the whole path in two calls: `done` with the product
  missing refused in 52 ms with the verdict and its item line; `done` with the product present
  passed in 60 ms. The journal holds `verification_requested`, `done_refused { verdict }`,
  `verification_requested`, `done { verdict, from: running, to: done }` in that order, each
  refusal carrying its own `effect_id`, which is what the decision claims.
- Every refusal the model reads names the field and its legal values. The one finding, P3
  below, is the reverse case.
- P3 (polish): `start`'s refusal for an unservable criterion prints the absolute artifacts
  directory. It is the store's own path under the user's repo, not a secret, and the same
  shape as the other store errors, so it is left as it is.
