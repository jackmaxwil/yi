# D102: a declared output schema is checked at `done`, not merely resolved

Status: accepted

## Decision

The resolve seam serves bytes. `OutputResolve`
(`crates/runtime/src/plan/ops.rs`) is one method, `resolve(&Url) ->
Result<Option<String>, String>`, shaped like `crate::fetch::CheckpointShow`,
and `crate::fetch::Resolver` implements it over `fetch`. The `Option` is the
load-bearing part: `Ok(None)` is **resolved-but-unserved**, minted from
`FetchError::Unsupported` alone — a scheme this resolver has no backend for
cannot adjudicate a schema, and a missing reader must not read as a missing
referent. Every other `FetchError` — denied, external, outside the workspace,
bad address, not found, stale, backend — comes back as `Err` and refuses the
op.

`do_done` uses it twice. When the todo's delegation declares an output schema,
`done` with no output reference is `MissingDeclaredOutput`; with one, the
engine fetches the product at that URL and the schema document the delegation
named, and only when **both** were actually served does it call
`validate_product`, which parses the document, extracts a JSON value from the
product with `crate::schema::extract`, and validates one against the other
through `crate::schema::Schema` — the same B4 validator the structured-output
path already used. A failure names what failed: `UnusableSchema` when the
schema document is not JSON, `OutputMismatch` carrying the validator's own path
string, which is `$`-rooted and points at the field. `check_terminal` still
runs afterwards, so an ephemeral terminal record is refused exactly as before.

Four tests in `crates/runtime/tests/plan_ops.rs` carry it:
`a_declared_output_is_validated_against_its_schema`,
`a_product_that_satisfies_its_schema_completes`,
`a_schema_that_is_not_json_refuses_the_done_naming_the_schema`, and
`a_declared_output_must_resolve_at_done`.

Beside it, two reap properties that are the same defect seen from two sides.

**A reap is idempotent at the delegate seam.** `SessionDelegate::reap`
(`crates/runtime/src/plan/dispatch.rs`) opens with `if
!self.host.holds(agent.as_str()) { return Ok(None); }`. `SubagentHost::holds`
is the same `key_of` lookup the reap itself would do, asked as a question
instead of as a refusal: a reap asks that a child not be running, and a host
holding no such child has already answered it.

**`supersede` runs every refusable check before the first kill.** `do_supersede`
builds the whole next cut — bumped version, new todos — and runs `validate_plan`
and `precheck_plan` on it, so both the cut's structural validity and the 32 KiB
frontmatter cap are settled before `reap_superseded` touches anything.
`a_supersede_refused_on_its_new_cut_kills_no_child` is the regression test, and
`supersede_is_atomic_when_a_reap_fails` still holds the D97 property beside it.

## Rationale

§3 said "declared implies Done requires validated output" and what shipped was
an existence probe. An existence probe passes on any file that exists,
including entirely the wrong one — a stale artifact from a previous attempt, an
empty placeholder, a product in the wrong shape. That is not a weaker check
than the design asked for; for the failure it was meant to catch, it is no
check at all, because the interesting way for a delegated product to be wrong
is for it to be present and wrong.

Making the seam serve bytes rather than a boolean is what closes it, and it
costs one `Option` in the signature. That `Option` is where the honesty lives:
if the seam collapsed a missing backend into a refusal, then attaching a
resolver with fewer backends would start failing `done` for todos that were
perfectly complete, and the CLI resolver — which attaches almost nothing — would
be strictly worse than no resolver at all. `Ok(None)` keeps a thin resolver
silent instead of wrong.

**The two reap properties are one bug from two sides.** `supersede` used to
refuse *after* killing part of the family, and the next attempt then refused on
the first already-dead child. Together those wedged a plan permanently: a
cascade that failed halfway could never be superseded again, because retrying
it hit a child the failed attempt had already taken and stopped there. Neither
half fixes it alone. Checking before the first kill makes a refused op leave
nothing dead, and the idempotent reap is what lets a retry walk past the
children a *previous* partial cascade already took. The fix is deliberately
placed at the seam rather than at the call sites, so every reap path inherits
it — `step_todo` remains the single writer of todo state and the single site
that reaps on leaving Running.

## Reversal path

Drop `validate_product` and the two refusal variants it mints
(`PlanOpError::UnusableSchema` and `PlanOpError::OutputMismatch`), and the
resolve seam degrades to the existence probe: `OutputResolve` returning
success or failure, with `do_done` asking only whether the referent is there.
Restore the `key_of` refusal in `SessionDelegate::reap` in place of the `holds`
check, and move `validate_plan` back after the cascade in `do_supersede`.
`crates/runtime/src/schema.rs` is untouched by any of that — it has its own
consumer in the structured-output path.
