# D60: a tool result carries a typed record of what it did

Status: accepted

## Decision

A tool's result carries a typed record of what it did in `details`, beside the
prose `content` the model reads. `edit` and `write` put the unified patch they
computed there under `patch`, `added` and `removed`; `ipython` puts its source,
`stdout`, `stderr`, `result` and the structured `KernelError` there, its streams
kept apart rather than joined. The transcript renders from that record instead of
re-deriving one from the tool's prose. The `content` string is unchanged, so the
model sees exactly what it saw before.

## Rationale

The patch was already computed at every write site and thrown away one layer
below the screen. `edit` builds it to apply the change, `write` needs the prior
bytes to describe what it replaced, and both then flattened the result into a
sentence like `updated; first change at line 2`. That left the transcript two
options, and both were bad: keep the one-line digest, or write a second diff
implementation that re-parses prose the tool had already turned into English. A
renderer reconstructing structure a producer discarded is the shape that ships
drift, because the two derivations are free to disagree.

`details` is the field §19 already reserves for exactly this, and the evolution
is additive: the key is optional, so sessions written before this change keep
parsing, and sessions written after replay with their diffs intact. Nothing
renames, nothing is repurposed, and every consumer already treats the keys as
optional — which is also what makes the reversal cheap.

Two details are deliberate rather than incidental. The write tool reads the file
before writing, because nothing else reconstructs the ground it replaced, and a
patch without the old side is not a patch. A no-op edit sets no key at all rather
than claiming an empty patch: absent and empty mean different things to a
renderer, and only one of them is true.

The cost taken knowingly is the kernel cell's source stored twice — the
assistant's own tool call already carries it. Storing it again on the result
means replay needs no cross-entry correlation to render a cell: the record is
self-contained, and a transcript replayed from disk shows what a live one showed
without walking backward to find the call that produced it.

## Reversal path

Drop the `details` assignments in the three tools; every consumer already treats
the keys as optional.
