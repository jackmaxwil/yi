# D370: `is_error` on a tool result means Yi could not do what was asked (the...

Status: accepted

## Decision

`is_error` on a tool result means Yi could not do what was asked (the arguments were
refused, the command could not finish, the sandbox refused it, a safety refusal); a
command that ran and exited non-zero, and a call the tool understood and a rule
answered no (`details.errorKind` `verdict`), are results: bash sets `is_error` only
for a cancelled or timed-out run or a sandbox refusal and keeps `exitCode` in
`details`, and the tool adapter turns a verdict into an unflagged result that keeps
`details.errorKind` `verdict`, for every tool; what a person is shown reads
`yi_types::event::shown_failed`, which is `is_error`, a non-zero `exitCode` or a
verdict, so the TUI card keeps its cross, ACP its `failed` status, user rules scoped
to errors still fire on a failing command, and the todo coupling still counts a
failed command as nothing landed; the model, the provider's `is_error` flag,
telemetry and `yi stats` see the call as a result, and the session miner's failure
census reads the same rule as `shown_failed`, so it still counts a non-zero exit and
a verdict, each in its own class

## Why

The owner chose "No, it's a result" for a command that ran and exited non-zero and
fixed what counts toward the zero-failure target as "Misreads + stale state";
prompts 03 and 11 of the dogfood ask for a cycle and a done before the fix, and
flagging the engine's correct answer as an error made the model treat it as a fault
to repair; row 0073 counted 8 verdicts and 5 command exits among 43 failures

## Reversible via

Delete `verdict_is_a_result` and `shown_failed`, and set bash's `is_error` from the
exit code again
