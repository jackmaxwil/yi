# D322: one list of credential stores, judged by file identity (amends D180 and D296)

Status: accepted

## Decision

One list of credential stores, judged by file identity (amends D180 and D296):
`~/.yi/providers/tokens` joins `.ssh`, `.gnupg`, `.aws`, `.kube`, `.docker` and
`~/.yi/mcp/tokens` in `PROTECTED_CREDENTIAL_SUBPATHS`, and
`yi_permission::credential_stores` is the list the destroy gate, the read gate, the
bash read belt and every sandbox profile's deny-read take (the sandbox's own
`CREDENTIAL_DIRS` is gone); a named read or grep `path=` is judged by
`ReadGuard::denies` on the path as the tool opens it, `..` taken after the link
before it, and refused when the path or an ancestor has the device and inode of a
store, `/dev` or the workspace `.git`, when the path is `/`, `/home`, `/Users`,
`/root` or the home by identity, or when its spelling or its canonical spelling
meets D180's list; a walk takes the same guard, once for its root and by each
directory entry's own identity; yi's own reads of its tokens and config are host-
process opens and meet none of this; `~/.yi/config.json` stays readable

## Why

A provider login under `~/.yi/providers/tokens` passed read, grep and a contained
`cat` (#887); D180 compared spellings, so `~/.SSH/id_rsa`, `link/id_rsa`,
`link/../.ssh/id_rsa`, `/private<home>/.ssh/id_rsa` and the `/System/Volumes/Data`
firmlink reached a key while #885 already judged walks by identity (#898); the
config holds no key (the strict `UserConfig` has no secret field, `keys` is the
keymap) and every `yi` reads it before dispatch, so denying it would end the
kernel's contained `yi mcp` with exit 2

## Reversible via

Restore the lexical `read_is_catastrophic` and `resolve` in `decide`, and
`CREDENTIAL_DIRS` in `sandbox.rs`
