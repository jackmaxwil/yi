# D86: Heartbeat lanes are in-process, keyed by session_id

Status: accepted

## Decision

H7 lanes run in the one `Scheduler` process: after the H5 claim-before-deliver, claimed jobs are
grouped by `Job.session_id` (empty string is one lane). That id is the ACP/session-store id, not
the `rlm-{pid}` directory name. Each lane delivers serially on `spawn_blocking`.

Lane tasks are **kept across timer ticks** in a `JoinSet` and reaped by task id, so a session
with a lane still in flight is simply skipped at claim time and the timer never waits on it. The
timer's next deadline is the soonest job *outside* the busy set (`next_claimable_run_at`), and it
parks in a single `select!` over three things: that deadline, the store's change notification,
and a lane finishing. The change waiter is registered before the snapshot it is about to act on,
because `JobStore::mutate` wakes with `notify_waiters`, which stores no permit for a waiter that
arrives afterwards.

One `JobStore` and timer is interned per `scheduled-jobs.json` path so two sessions on one worker
share lanes. `DeliveryHub` holds one `deliver` closure per bound session and clones it out from
under its mutex before calling it. A session's `HeartbeatService` withdraws its lane from the hub
when it drops, and a heartbeat armed before the session store is attached is refused rather than
stamped with the empty session id.

A second daemon process is not required.

## Rationale

One blocked sync `DeliverFn` on the timer task starved every other claimed job on the shared
`JobStore`. Isolating workers per root does not fix two `session_id`s in one
`scheduled-jobs.json`.

Grouping by session was necessary and not sufficient, and each remaining hole was proven with a
failing test before it was closed:

- `DeliveryHub::dispatch` held the lanes mutex across the whole `deliver` callback, so in the
  only production wiring every session still serialized on one lock — the exact starvation the
  lanes exist to remove.
- The timer awaited every lane before its next tick, so a sibling that became due *during* a
  block never dispatched until the block ended.
- The replacement parks were still a bare `join_next().await`. A blocked session whose own
  interval re-armed made every claim come back empty, and a blocked session whose only job was
  `Once` left no deadline at all; in both cases the timer froze exactly as before. A 60s
  heartbeat parked behind a five-minute turn hits the first one every time.

The interned store is what makes the lanes real at all: without it every job carried
`rlm-{pid}`, so there was one lane per worker rather than one per session, and two sessions on a
worker replaced each other's heartbeat.

Concurrent blocking lanes keep H5 (claims persist before any `deliver`) and H6 (a panicked lane
leaves unresolved claims for recover-on-start). Withdrawing the lane on drop is what keeps
"dropping the session stops the timer" true now that one interned timer outlives every session
sharing its ledger; without it an ended session's still-Active heartbeat fires into a stale
closure for the life of the process.

## Reversal path

Restore the serial `for dispatch in claimed` loop in `Scheduler::start`, delete `lanes.rs` and
`shared.rs`, and drop `HeartbeatService`'s `hub` and `deliver` fields along with its `Drop`.
`next_claimable_run_at` collapses back to the earliest active `next_run_at`.
