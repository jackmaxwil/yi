# D391: `models.selector` names a model that picks lines

Status: accepted

## Decision

`models.selector` names a model that picks lines: after the reducer or the capture
cut a bash output (the tool's own `truncated` or `outBytes < rawBytes`, never the
text), and only when its `[full output: …]` pointer resolves inside the session's
spill dir, the full output's numbered lines, at most 4,000 and 256 KiB (`LINES_IN`,
`BYTES_IN`, named in a row when skipped), go to it with the command and its exit
code, and it answers 1-based inclusive line ranges only, through a JSON schema; Yi
keeps the ranges inside the output, merges overlaps, caps them at 200 lines
(`LINES_OUT`), and appends those lines numbered under `[lines a-b, … of the full
output, selected by <model> (models.selector); kept N of M selected lines (LINES_OUT
200)]`; no answer within 5 s (the request is cut and its cost named unknown), an
answer that is not ranges, or a provider fault appends `[models.selector <model>
gave no lines (<reason>); the cut above is the reducer's alone]`; a cancelled
command asks nothing; the cost is booked `side:select`; unset, nothing is asked

## Why

The owner asked for both deterministic reduction and a learned selector ("Both B and
C"), the selector only as line ranges so it can drop but never invent; the bench
(eval-ledger 0078, 0079) found every answered case covered its gold lines on
deepseek-v4.1-flash and most on glm-5.3-flash, but both missed the 5 s deadline on a
1,458-line build every time, so the gate (recall >= 0.85, p95 < 3 s) is not met and
the selector stays off unless named

## Reversible via

Drop the `selector` key, `select.rs` and the adapter's call
