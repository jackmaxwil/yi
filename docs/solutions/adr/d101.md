# D101: the corpus is one address space behind one seam

Status: accepted

## Decision

`Transcripts` (`crates/runtime/src/fetch/mod.rs`) is the seam: one method,
`open(agent) -> Option<SharedSession>`. Everything that reads a transcript goes
through it, and the resolver's `transcript_of` is the whole precedence rule —
the attached session if the address is its own agent, otherwise the desk.

`TranscriptDesk` is the late-binding half. Composition builds the resolver
before the subagent host exists, so the desk is handed over empty and filled in
once with `attach`, the same shape `KernelServiceMap` already used for kernels.
`SessionTranscripts` is the implementation behind it: a live child first
(`SubagentHost::transcript`, which resolves the target through the host's own
key lookup and returns the child's store), then the corpus on disk — a
`JsonlRepo` over the sessions dir, opened by session id.

Both schemes route through it. `resolve_history` tries the **whole path as an
agent** before splitting anything off, and only if that misses does it
`rsplit_once('/')` into agent-plus-entry and try again; when neither hits and
no store and no desk are attached at all, the refusal is `Unsupported` naming
the missing backend, and otherwise it is a `NotFound` that says the address is
"not the attached session, not a live child, and no session on disk carries
that id". `resolve_agent` asks the desk before it asks the log: a running child
answers its own `agent://` URL, served as `live-child <path>`, and only a child
the desk cannot open falls through to the reap pin and resolves whatever that
pin points at.

The tests at the bottom of `crates/runtime/src/fetch/schemes.rs` carry it. A
stub `Desk` stands in for the host, and
`a_reap_pin_named_like_a_todo_address_still_resolves` pins a two-segment
address and asserts the transcript comes back served by `session-transcript`;
`a_live_child_answers_its_own_agent_url_before_any_pin_exists` asserts the
`live-child` provenance with no pin in the log at all.
`history_resolves_entries_through_the_attached_session` and
`a_reap_pin_lets_agent_urls_resolve_after_the_child_is_gone` are the D98 tests,
unchanged and still green.

## Rationale

D98 shipped `history://` with two defects that concealed each other, and the
test that should have caught them was the reason neither surfaced.

**The split was at the wrong slash.** `history://<agent>[/<entry>]` was read as
agent-plus-entry at the *first* slash. But an agent name is a todo address and
carries its own slash: `SessionDelegate::reap`
(`crates/runtime/src/plan/dispatch.rs`) registers `agent://<plan>/<todo>` →
`history://<plan>/<todo>`, and the first-slash split read that target as the
plan plus an entry id that never existed. So **no reap pin resolved at all** —
the promotion-at-reap path that D98 built the pin ledger for was dead in
practice. The old unit test passed because it hand-pinned a single-segment
address, which is the one shape a reap never mints. Trying the whole path as an
agent first is what fixes it, and it is the right precedence independently: the
agent segment is the greedy one because the entry id is the optional tail.

**The corpus stopped at the attached session.** `history://` served only the
agent the resolver was attached to and named it in the refusal, which D98
recorded as a bound waiting on a store that could open a session file it was
not attached to. That bound is what made promotion-at-reap pointless in the
other direction: the payoff of promoting a dead child's trace is that a retried
child can read what the failed attempt did, and a resolver that can only see
its own session cannot serve it.

Ordering live-before-disk is what makes a running child inspectable at will
rather than only after it dies. The two halves of a child's life — running, and
reaped — become one address, and the caller does not have to know which it is
looking at; the `served_by` string still says, so provenance in the fetch log
does not blur.

The seam is a trait with one method on purpose. Everything expensive or
stateful — the host's child map, the JSONL repo, the sessions dir — lives
behind it, so the resolver stays a match over schemes with no knowledge of how
a transcript is found, and the CLI resolver simply attaches nothing and reports
what it lacks.

## Reversal path

Drop `Transcripts`, `TranscriptDesk` and `SessionTranscripts`, and
`resolve_history` falls back to the attached session alone. `resolve_agent`
then resolves through the reap pin only, which is D98's behavior. The pin
ledger, `register_pin` and the `agent://` scheme are unaffected — this row
changed who can be opened, not how a pin is minted.

Source of truth: the decision log in docs/ARCHITECTURE.md (D101). The resolver
and the pin ledger this extends are D98, the reap that mints the pin is the
delegate seam of D97, and the corpus reach D98 recorded as a bound is the one
this closes.
