# D118: the daemon's session ledger lives on disk beside the socket

Status: accepted

## Decision

The daemon keeps its per-session ledger — `cwd`, `unseen`, `lastState`,
`lastEventMs` and `name`, keyed by session id — in `<socket>.ledger.json`, the
socket path with its extension swapped (`~/.yi/daemon.sock` →
`~/.yi/daemon.ledger.json`). The shape is `yi_types::acp::DaemonLedger`, a
durable struct under the §19 rules: camelCase wire names, optional fields
defaulted, unknown fields carried in a flattened `extra` map, and a golden
fixture at `crates/types/tests/fixtures/daemon-ledger-v1.json`.

The file is rewritten whole, through a temp file and a rename, at every point
the ledger changes: a worker's state transition, the first prompt that names a
session, a `_yi/seen`, and a `session/new` or `session/resume` result.
Attachment changes do not write; the attached set is per-connection state and
is not stored. Provisional rows — the ones the pre-attach path invents so a
resume's replay can route — are filtered out of the file.

At boot the daemon reads the file back before it accepts a client. Every stored
`lastState` reloads as `idle`: no worker outlives the daemon, so a stored
`running` or `requires_action` is a turn that died with it.

The same row moves `lastEventMs` from every streamed worker frame to the state
transition that also counts unseen. Activity is a transition, not a chunk.

## Rationale

The console's sidebar lists the sessions of its own root from that root's
worker, which reads the session files on disk, and the sessions of every other
root from the daemon's ledger, which until this row lived only in memory. With
one repository checked out as a dozen worktrees, every daemon restart —
ctrl+c twice, `just dev`'s rebuild loop — emptied the sidebar of every session
but the current root's until each was resumed by hand, and took the unseen
counts and the first-prompt names with it. That read as chats vanishing.

Rebuilding the list from the session files instead was weighed and rejected.
The daemon would have to spawn a worker per root ever used to ask each for its
list, or grow a second reader of the worker's repository format. The ledger is
a few hundred bytes and already holds everything a `session/list` without a
cwd answers with.

Per-chunk `lastEventMs` was the other half of the sidebar's instability: two
sessions streaming at once leapfrogged each other on every list, and the
console only refreshed the stamp after a prompt, so rows jumped in bursts at
moments unrelated to what the user was watching. Stamping the transition gives
both sides the same discrete clock.

## Reversal path

Delete `DaemonLedger` and `DaemonLedgerEntry` from `yi-types`, `load_ledger`,
`ledger_path` and `Supervisor::persist` from the daemon; the ledger is
in-memory again. The fixture stays, as every fixture does, as a record of the
shape that was written.
