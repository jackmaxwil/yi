# D472: an interrupt's fire sets the current request's cut flag as well as `fired`,...

Status: accepted

## Decision

An interrupt's fire sets the current request's cut flag as well as `fired`, and each
request opens with a fresh cut flag, so one abort stops the provider pump on the
wire and a later request never clears an earlier one's cut (amends D163, which had
only the loop set the cut)

## Why

After Esc the provider kept generating, and billing, up to `max_tokens` while the
loop had stopped listening: on Kimi's recorded 91-event bash stream an abort at the
third event read all 91, and with one shared flag the next prompt's request cleared
the abort's cut before the old pump read it

## Reversible via

`fire` stops setting the cut and `clear_cut` stores false into one shared flag again
