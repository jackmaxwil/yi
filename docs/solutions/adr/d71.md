# D71: Yi speaks MCP itself

Status: accepted

## Decision

`yi-mcp-cli` implements JSON-RPC 2.0 directly — line-delimited over a child
process, or POSTed over the tree's one ureq stack for streamable HTTP. `rmcp`
becomes a dev-dependency, serving `examples/reference_server.rs`, which the
client is tested against. `sse-stream`, `futures-util` and `http` are dropped
outright.

## Rationale

§13.3 rejected a hand-rolled client in one line: "protocol churn outpaces a
private impl; official SDK tracks spec". That is a real argument, and
measurement inverted it.

rmcp cost 683,760 bytes of a 4.6 MiB binary — `yi-mcp-cli` alone weighed
623 KiB of `.text` from 2,405 source lines, more than `std` — and earned none of
it. All six ops in `client.rs` ended in `to_value`, so Yi instantiated rmcp's
entire derived model layer to rebuild JSON that had arrived as JSON.
`ServerResult::deserialize` was 20.4 KiB; `ClientRequest::serialize` appeared
three times, surviving fat LTO.

The second fact settled it: `http.rs` was *already* a hand-rolled ureq transport
with its own SSE frame parser, 338 lines written to satisfy rmcp's
`StreamableHttpClient` trait shape, while `crates/ai/src/sse.rs` was a second SSE
decoder Yi already owned. The dependency was being adapted to Yi, not the
reverse. What remained of rmcp was the part Yi does not use: §5.2 is one-shot —
connect, negotiate, run one op, exit — so the service layer, worker tasks and
cancellation model a lifecycle that does not exist here.

The churn argument also cuts the other way. Yi passes the server's `result`
object through as a `Value`, so a field the spec adds tomorrow survives. A typed
model rejects what it has not learned. The rewrite is more tolerant of drift than
the SDK was, not less.

Two behaviours changed on purpose. Yi now identifies itself as `yi` in
`initialize`; before, every MCP server was told it was talking to `rmcp` 3.1.4.
And list and call ops return the server's own result rather than rmcp's
re-serialization of it.

One regression was caught by the suite and is worth recording, because it is the
shape of failure a dependency swap produces: `run` decided that a 401 should hint
`yi mcp login` by sniffing rmcp's error prose for "Auth required" or "status
401". Those strings left with the dependency and the hint died silently. The
marker is now a named constant with a test pinning it to what `AuthRequired`
actually renders, so the coupling is enforced instead of hoped for.

Testing is against rmcp itself, as a server. The client drives a real MCP
implementation over a real pipe for the handshake, `tools/list`, `tools/call`,
a multiline argument and an unknown-tool error. The suite was watched failing for
the right reason before it was believed: renaming `tools/call` to `tools/kall`
turned three of those tests red with the server's own `-32601`. An earlier probe
that broke the advertised protocol version left every test green, which is how
the unit test pinning what `initialize` sends came to exist.

Twelve crates leave the graph, `chrono` and the whole `tracing` tree among them,
so two deny.toml wrapper exceptions for §13.5-banned crates are deleted rather
than carried. Direct dependencies go 20 to 16, back to §13.6's stated ceiling.

The obligation accepted — tracking the MCP spec by hand — is the one D40 already
accepted for ACP, against a protocol surface of six methods and one handshake.

## Reversal path

Restore the four §13.3 rows and the rmcp call sites. `Op` and
`one_shot_with_auth` keep their signatures, so `lib.rs` is untouched by the
reversal.
