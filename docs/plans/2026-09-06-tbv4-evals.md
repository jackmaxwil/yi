## 0. What this plan answers

Issue #100's gate is a ledger row from a real Terminal-Bench run. Since it
was written the benchmark moved: v4 replaced every TB2.1 task, gave every
task an eight-hour agent timeout, moved the verifier into its own container,
dropped the reward-hack column for an LLM judge over an ATIF trajectory, and
closed community submissions (`tbv4-evals/tbv4-design.md` §1-5). The
six-task TB2.1 subset `evals/drivers/tb21_baseline.sh` pins lives in
`archive/` now, and the driver itself carries two defects, one of which lets
the $20/$25 cap fail open (`yi-fit.md`, "the harbor driver").

The user's question is wider than pass rate: coding performance,
persistence, quality of the experience, engineering rigor, against speed,
tokens and cost. The prompt-surface work shipped the instrument for the
middle three (`extract.py` v4, twenty signals; the todo tool's
`custom{todo}` and `custom{todo_intercept}` entries), and the standing rule
says those axes are measured with that instrument, never with a new judge.

So: one stdlib scorer that reads any run directory and prints the five-axis
row; the v4 harbor path repaired and pinned for the pass and economy axes;
Yi-owned tasks in harbor's format and the journey prompts for the rest;
every run user-run, capped in code, and a ledger row before any claim.

## 1. Laws (inherited; a step that breaks one is not a step)

1. **Deterministic control** (D54, prompt-surface law 1). Every column is a
   function of the run's artifacts. No model judges persistence, rigor,
   experience or reward hacking on our ledger. v4's `/judge` is the
   maintainers' tool for their leaderboard and is not run here.
2. **User-run, ledgered, capped** (flywheel law 3; D133's tier T3-live is
   the one exception and it is the live lane, not this). A v4 run is started
   by a person, spends against `tb21_cost.py --soft 20 --hard 25`, and
   appends a row to `docs/eval-ledger.md` before any commit cites it. Never
   scheduled, never inside `just check`.
3. **Issue before changelog row; ratchets in their own commit; stdlib only
   under `evals/`; no new dependency outside §13.3.** harbor is the host's
   install (`uv tool install harbor`), imported by the adapters, never a
   requirement of the tree.
4. **Additive ledger.** New columns on the right; old rows stay readable.
5. **Timeouts are results.** A timed-out trial is a row with `timedOut`,
   never a retry; harbor's `-k` attempts are the only repetition.
6. **Defaults are what is benchmarked.** The scored config is `yi ask
   --json --yolo` with the shipped prompt; a variant is its own row with its
   own fingerprint.

## 2. The design in one paragraph

`evals/axes.py` (stdlib, imports `signals` and `extract_session` from
`skills/yi/session-mining/extract.py` by path, the way `ab.py` shells to it)
takes a directory and finds every trial in it, whether harbor's
`jobs/<job>/<trial>/` (`result.json`, `logs/agent/yi.jsonl`,
`logs/agent/yi/sessions/*.jsonl`, the telemetry sidecar), `run.py`'s
`--out/<task>/`, or `ab.py`'s `<ref>/`. For each trial it computes the
columns in `axes.md` (pass, persistence, rigor, experience, economy), prints
one JSON line per trial and the ledger row with the three new triples on
the right, and exits 2 when any trial is unmeasurable (`usage.unknown`,
no session file). The harbor driver becomes `tbv4_baseline.sh`: the digest
pinned, `-i` and `-o` correct, the cost probe over the directory harbor
writes, `--agent-timeout-multiplier` carried into the config fingerprint.
Three Yi tasks gain harbor's layout so the same directory runs in both
runners. Nothing in `crates/` changes.

## 7. What is not built, with the reason

- **An eval permission profile (E3 as YI_DESIGN wrote it).** v4's separate
  verifier reads only declared artifacts and never sees `/tests`; the risk
  moved to a judge no rule addresses (`yi-fit.md`). The mechanism
  (`ConfigRule`, deny-first `decide()`) stays for pier.
- **A reward-hack judge of our own.** Law 1. The trajectory is read by the
  person who cites the row.
- **A composite score.** Five axes on one row; a number would be optimised.
- **`answer.txt` in the harbor adapter.** Not a v4 contract; the SWE-Atlas
  QnA suite is a separate issue when it is pursued.
- **Any model but `openrouter/z-ai/glm-5.3-flash`.** Every ledger row is
  flash; a frontier row is not on this plan.
- **An eight-hour trial.** The driver caps the multiplier at 0.125; the
  row's notes name the discrepancy with the instruction's "28800 seconds".
- **A leaderboard submission.** Closed to the community
  (`SUBMIT.md:3-4`); a subset with a multiplier would be rejected by
  `static_analysis.py` anyway. The ledger row cites the public reference row
  for scale and says it is not comparable.
- **Running the full 66 tasks.** 66 × 8 h × k=5 is the maintainers' 330-trial
  job ($7,265 on a frontier model). Not a slice; not this quarter's question.

## 8. Decisions taken (2026-09-06, the user's answers)

1. **Model: `openrouter/z-ai/glm-5.3-flash` only.** Every row on this plan
   is flash; the leaderboard's frontier rows are cited for scale and never
   for comparison. The driver hard-codes the model as `tb21_baseline.sh:10`
   did.
2. **One hour or less.** `--agent-timeout-multiplier 0.125` is the default
   and the ceiling; the driver refuses a larger value. The instruction's
   "You have 28800 seconds" is the task's text and stays; the row's notes
   name the discrepancy (E12).
3. **ATIF now.** S4 lands before any paid run; `SUPPORTS_ATIF = True` on the
   adapter; every trial the ledger cites opens in `harbor view`.

No open questions remain.
