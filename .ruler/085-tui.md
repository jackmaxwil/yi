

# TUI work

Verification (the phase-7 lessons, paid for once):

- Any TUI behavior change runs the headless drive mode before it is claimed
  done: `yi tui --headless --keys <script> --frames <dir>` drives the real
  loop over an in-memory screen with scripted keys and dumps text frames.
  Visual changes include a frame dump in the report.
- A change a person has to look at ships a proof artifact: `just tui-proof
  <script>` records the same drive run as an asciicast (`--record`) plus a
  one-frame still cast (`--snap`) and renders `run.gif` / `still.gif` for the
  PR. Frame dumps prove the contract held; they cannot show whether the result
  looks right, which is the half a model judges worst. Render stills with a
  terminal emulator (agg), never a text-screenshot tool: `freeze` re-renders
  in its own font and chrome, so its output is not the grid Yi painted. Pace
  typing with `type-ms <n>` and raise `--deadline` when the beats outlast 60 s.
- vt100 tests for viewport code must include a nonzero-offset case: an
  inline viewport at row 0 hides every coordinate-origin bug (the blank-frame
  draw-offset bug shipped exactly this way).
- Terminal protocol features (kitty graphics, OSC titles, DEC modes) require
  reading the protocol's lifecycle semantics first, and the load-bearing fact
  goes into an incident comment (kitty placements scroll with the text under
  them; inline-viewport init blocks on a CPR reply stdin must answer).
- The true-terminal path (raw mode, CPR, kitty flags) is verified with
  `scripts/tui_pty.py` — a PTY harness that answers cursor-position queries
  and sets a real winsize; plain `script(1)` cannot, no emulator answers.
- A capability path is only exercised when the capability is actually
  advertised: the PTY harness pins the child's `TERM`, so every graphics-path
  run before `--term xterm-kitty` existed silently took the fallback and
  proved nothing. Check that the path under test ran — count the emitted
  escapes — rather than inferring it from a clean exit.
- The faux provider answers instantly, so no draw ever observes a turn in
  flight; anything scoped to a running turn (spinners, morphs, live regions)
  cannot be verified end-to-end with it. Test the state transition and the
  per-frame math directly instead of asserting on a run that never animated.
- Frame-paced animation reads its own elapsed clock, and a surface that stops
  repainting when it settles hands the next frame an unbounded gap. Clamp a
  step to one frame; the unclamped version consumed a whole animation in its
  first frame and looked like an instant snap.

Reference-first UX: before implementing any user-facing TUI surface, read how
the §8.14 donor references do it and present
that as the default; a smaller fresh implementation is a deviation to
confirm, not a starting point. String-cell tables that dropped inline code
and a braille orb renderer both shipped before this rule existed.

Visual approach gate: rendering-medium and aesthetic decisions — a new
renderer, a layout paradigm, an animation system — get a one-screen proposal
or a static mock and user sign-off before implementation. A medium that
cannot carry the design's depth language (braille: binary dots, one color
per cell, vs radius + ink) is rejected on paper, not after two tuning
rounds.

Streaming renders commit by byte cursor over standalone slices, never by
line counts derived from re-rendering a growing prefix — renderers trim
trailing blanks and the counts drift (the duplicated-list bug).

- A frame assertion reads the row: `row_text` on the VT100 backend in-process, a whole-row
  needle in `wait-frame` in a drive script. A substring over the screen proved "python" was
  somewhere while the row it sat on said something else. The window title is an OSC sequence
  and never reaches a frame (capture.rs), so it is asserted on `App::pending_title`.
